# 自主回复只让判断模型指认批内候选：隐藏非候选编号，候选改用批内标签

状态：已采纳（2026-10-28）。

群聊自主回复的判断模型原先拿到的是与 `history` 同一空间的全局流水号，`candidateIds` 只是这个空间的子集。模型返回一个不在子集里的编号时，代码只能记一行「判断失败，不回复：回复判断选择了本批次之外的消息」并放弃整轮——`pending` 在调用模型前已清空，这批消息不会再被判断。日志不是问题的来源：协议本身让模型有机会指认一条本轮不允许回复的消息，而且编号长得像可以随手编的数字（机器人自己的发言、@机器人消息、上一轮旧消息的编号都直接摆在眼前）。

现在的协议是：**只有候选消息带编号，而且这个编号只在一批内有效**。`history` 里机器人自己的发言、@机器人消息、指令、超限用户消息和已过轮次的消息一律不携带编号字段，候选条目带 `candidate: "c2"` 这样的批内标签；模型只能原样复制标签，标签经小写与去空格归一化（也接受纯序号 `2`）后仍映射不到候选时不回复，并在日志里记下模型原始返回值。

## 考虑过的替代方案

- **保留全局流水号，只加类型归一化**：能修掉「模型返回数字、Map 键是字符串」这一类，但协议仍允许模型引用旧消息，语义越界这一类不减少。
- **让模型给每个候选打分，代码取最高**：模型不再选编号，看似最稳，但输出变长、漏项与多项成为新的失败面，一次判断的 token 成本随候选数线性上涨。
- **模型只给分数，代码统一绑本批最新候选**：彻底消灭非法编号，代价是引用目标从「模型选的那条」变成「最后一条」，多消息批次里会引错，与「引用绑定判断模型选中的原事件」的既有契约冲突。
- **给四个 provider 加 `response_format` / `responseSchema`，用 enum 钉死编号**：约束最强，但四家字段与兼容性不一致（OpenAI 兼容端点常静默忽略 `json_schema`），且 `SubLLM` 被翻译、记忆提炼等多处共用，风险外溢。
- **非法时兜底回复最新候选**：保住这一轮，但把针对 A 的评分用到 B 上，群里表现为答非所问的引用，比不回复更糟。
- **非法时纠正重问**：失败成本翻倍，而标签笔误是低频事件；等真实日志给出残留率再决定，现在不付这笔钱。
- **上锅巴开关**：这是内部协议，不是用户可调策略；`extraSystemPrompt` 已经提供了追加约束的出口。

## 已知约束

- **标签只在一批内有效**：不同批次都从 `c1` 开始，日志里的 `c2` 要连同该行一起读，不能跨行对照。
- **非候选消息没有编号就不能被指认**：模型想回旧消息时只能选一个候选，或给 0 分；这是刻意的，`history` 只承担上下文职责。
- **协议仍然只靠提示词**：`SubLLM` 没有结构化输出能力，模型完全可能返回 `c9`、数字或 `candidate` 字面量；代码不再把它当异常，只当这一轮不回复。
- **失败不再抛异常**：`run()` 的 catch 只覆盖真正的错误（非法 JSON、provider 不可用等），非法编号走正常返回路径；日志由两条降为一条是副作用，不是目标。
