# 引用的合并转发在入 core 前展开，工具只负责主动读取

状态：已采纳（2026-10-26）。

QQ 的合并转发是独立消息类型：引用它时，被引用消息里只有 `forward` 段，没有正文。插件此前的引用解析只取 image / text / video / file，导致模型完全看不到转发内容。现在分两条路：**引用**的合并转发在入 core 前自动展开成 Markdown 引用块（含媒体 URL），**聊天记录里其它转发**由智能模式工具 `view_forward_msg` 按 `[CQ:forward,id=…]` 主动读取；两者共用同一套拉取与渲染，预算为节点 50、字符 20000、嵌套 1 层、单次 10 秒。

## 考虑过的替代方案

- **两条路都走工具**：模型要先「意识到」上下文里有一行 `[CQ:forward,id=…]` 才可能调用。引用场景里这行还经常被输入侧的 CQ 清理剥掉（at 模式整段剥），并且引用内容本身就是用户这一问的上下文，让模型多走一轮工具既慢又容易漏。工具仍保留，但只负责「主动读聊天记录里的转发」。
- **两条路都自动展开**：群聊上下文会把最近 N 条消息的 `raw_message` 一起塞进 system，逐条展开意味着每条历史转发都要一次接口调用，条数与耗时都不可控；这些内容大多数与当前问题无关。
- **转发内图片走原生多模态**：把图片下载转 base64 直接内联，token 与请求体都会随节点数膨胀，且转发可能有几十张图；给 Markdown URL 让模型按需调用 `recognize_media`，才能把「读转发」与「看图」分成两次可省略的开销。
- **AstrBot 的做法（无上限）**：参考实现没有节点/字符上限，也没有主动读取工具。本仓要求第三方内容限长，且展开文本会随 prompt 持久化进会话历史，因此不能照抄。

## 已知约束

- 展开文本进的是 **prompt**，会与用户消息一起写进会话历史；预算不只防单轮撑爆，也防历史永久占用。失败提示同样是 prompt 的一行，只写一行，不写详情。
- **失败必须可见**：适配器不支持、超时、接口异常、空转发各给一行中文提示，让模型知道「没读到」，避免编造转发内容。
- **媒体 URL 的可信范围只覆盖媒体段**：只有 image / video 段真正携带的地址会登记为来源可信（沿用 ADR 0003 的分层，只放开私网/CGNAT/benchmark）；文本节点里出现的 URL 不登记。否则一句「看 https://内网地址」就能借转发的壳拿到可信身份。
- **工具只在输入侧保留 CQ 码**：输出侧 `removeCQCodeFocus` 继续移除全部 CQ——插件没有按 CQ 发送合并转发的通道，保留只会把裸 CQ 文本发到群里。
- **转发内部的 at 不产生 atBot 语义**：只渲染成 `@昵称` 文本。外层「合并转发 + atBot」在 QQ 上不成立，不写兼容分支。
- 拉取超时用 race 实现，底层请求无法取消；超时后迟到结果直接丢弃，不重试。
