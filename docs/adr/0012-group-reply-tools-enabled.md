# 自主回复重新装配工具：撤掉当天加的禁用开关

状态：已采纳（2026-10-28）。需求与决策过程见 `.scratch/group-reply-tools-rollback/spec.md`。

同一天里，自主回复先被摘掉工具，又被装回去。两次都是刻意的，这里记清楚，免得后来者翻到那次事故又把闸重新装上。

上午的事故是真的：群聊自主回复的正式回复走普通聊天路径，`enableSmart` 取全局 `smartMode`，智能模式一开就装配全部工具，模型顺手调了 `Memory_Tool`，把群里的闲聊写进记忆库。修法是接上 Core 里早就存在、但一直没人传的 `opt.disableTools`，并在锅巴加一个默认关闭工具的面板开关，留出放开的口子。

晚上撤掉的理由是产品判断：自主回复要像人一样说话，能查、能办、能记住。一个「要不要让机器人用工具」的部署开关，会让同一套行为在不同机器上分叉，也会让「它为什么不替我干活」变成必须翻面板才能解释的问题。闸本身没有错，错在把工具能力当成部署配置来管。

撤掉的范围严格限定在开关这一圈：面板字段、配置归一化里的键、只做一层转发的取数函数、聊天入口传参。Core 的 `opt.disableTools` 原样保留——它早于这次修改存在，是协议层「按次压制工具」的能力，还管着 Claude／Responses 的原生工具与 Gemini 的搜索、代码执行。现在它又回到没有生产调用方的状态，`groupReplyCore` 里覆盖它的用例继续保留。

## 考虑过的替代方案

- **保留开关但默认放开**：等于把同一件事留在两个地方表达，且默认值一改，历史机器上的行为仍不一致。既然结论是「就应该用工具」，开关本身没有存在理由。
- **只禁写类工具（记忆、发消息、代执行），保留查询类**：更贴近真实意图，但要给工具分类并维护这份分类清单，语义边界也模糊——「查」常常伴随后续写入。本次不做，留给以后有具体需求时重新评估。
- **在自主回复的提示词里要求「别用工具」**：约束强度取决于模型，且与本仓「工具注册由配置开关控制」的既有做法不一致，无法作为可验证的边界。

## 已知约束

- 事故路径重新可达：智能模式开启时，自主回复会装配全部工具，包括 `Memory_Tool`。这是有意接受的代价，不是遗漏。承担它的是群里的成员与部署者——他们看到的是副作用本身（机器人在闲聊里执行了一条指令、冒出一张图、某段话进了记忆画像），而不是一个「这是自主回复干的」的标记，事后很难归因到这一步。
- 面板上不再有任何控制自主回复工具行为的开关。要收，只能关掉全局智能模式，或者改代码。
- 老的 `config.json` 里若残留 `groupReply.disableTools`，无人读取，不影响行为。
- 已手动关过那个开关的部署者不会收到通知，升级后行为直接变回「有工具」。
