# Bot 响应白名单的闸门放在入站入口，不放在抽象对话层

状态：已采纳（2026-10-28）。需求与决策过程见 `.scratch/bot-reply-whitelist/spec.md`。

多开 QQ 与多适配器共存时，同一个群里的多个账号都会收到同一条消息，各自走一遍对话链路，于是出现重复答案与双份 token。新增的「Bot 响应白名单」按 `self_id` 放行，空列表 = 全部响应。

关键是闸门放哪。所有回复路径最终汇合在 `apps/chat.js` 的 `abstractChat()`，看起来是最省事的单点；但 `apps/ScheduleTaskPlugin.js` 也用任务里存的 `bot_id` 造影子事件直接调它。放在那里，白名单一变，昨天设好的定时提醒就不再响，而且没有任何提示。定时任务是用户显式预约的一次发送，不是对当下这条消息的响应，它属于出站。

所以闸门放在四个入站位置：`chatgpt()`、`chatgpt_for_firstperson_call()`、`otherMode()`，以及 `utils/groupReply.js` 的 `authorized()`——最后一处在候选准入时拦，省掉一次注定白跑的模型判断。其中 `otherMode()` 目前**没有 rule 接线**（`#chat1`／`#chatglm`／`#claude`／`#gemini` 这几个方法已不挂规则，也没有按钮派发），闸门留在那里只为这些入口哪天恢复时不必再补一次，不算当前生效的覆盖面。

## 考虑过的替代方案

- **放在 `accept(e)` 阶段**：不可行。框架 `deal()` 里 accept 返回 `"return"` 会终止**整条消息链**，连其他插件都不再收到；返回真值只是跳出 accept 循环、继续规则匹配。两种语义都表达不了「这条消息我这个插件不处理，别的插件照常」。
- **在每个 rule 的处理函数里各判一次**：`apps/` 下 19 个消息类、151 条 `reg:`（实测），外加 2 个全量观察器与 2 个 `notice` 观察器。既无法穷尽，也会把判定散成一份靠自觉维护的清单。
- **在规则层加一条高优先级拦截规则**：命中后返回真值等于终结消息链，同样会误伤其他插件。
- **同时管出站（定时任务、工具箱 OTP、主动打招呼）**：本次不做。工具箱遍历所有账号发 OTP 是刻意的多号可达性设计；定时任务按创建者账号回放是既有语义。收进来会改变已有行为，而它们都不是「响应触发」。

## 已知约束

- 只覆盖对话触发。`#结束对话`、`#gpt偷图`、meme、戳一戳、记忆采集不受白名单约束——把运维指令也静默，会让主人在非白名单号上以为插件坏了；静默记忆采集则等于换个号就丢记忆。
- 主人不豁免。豁免会直接破坏目的：主人在群里同时 @ 两个号，非白名单号仍会回一遍。
- 取不到账号身份时放行（fail-open）。单号 Yunzai v3、`ScheduleTaskPlugin` 自造的 `mockE` 这类路径可能没有可信的 `self_id`；fail-closed 的代价是整插件静默，比多号抢答严重得多。自主回复的准入不在此列：那里沿用既有的「取不到账号就不准入」前置，白名单的 fail-open 到不了。
- `utils/groupReply.js` 的准入处不打日志：`observe()` 对每条群消息都会调用它，打日志会刷屏；日志只留在三个显式入口。
- 被挡消息若同时命中第一人称正则，`chatgpt()` 与 `chatgpt_for_firstperson_call()` 会各打一条日志——两条都记在 `logger.info`，不落文件，且只在「消息含 AI 第一人称」时出现。
