# 本地读取通道：纯 HTTP + 本地转换，删掉浏览器与 Python

状态：已采纳（2026-10-21）。需求与票见 `.scratch/local-web-tools/`。

插件里一直有两个「不用任何 Key」的联网工具：`website`（网页读取）与 `web_search`（搜索）。到 2026-10 它们都已经不能用或不该用：

- 网页读取走 puppeteer，每次 `new ChatGPTPuppeteer()` 连 `127.0.0.1:51777`（没有就现起 Chromium），`finally` 里 `browser.close()`。如果连上的是共享实例，**这一下会把插件自己的头像/数学渲染一并关掉**；它还会临时改全局 `Config.headless` 再改回来，异常路径上改不回来；`page.goto` 用 `networkidle2` 且没有超时。
- 搜索用 `execSync` 调 `utils/web_search.py`，要求用户自己装 Python 3 + `aiohttp` + `beautifulsoup4`。实测这台机器 Python 在、依赖没装，工具直接返回「Python依赖缺失」。即便装好，它也是串行抓 N 个结果页、每条 700 字符、单页 6 秒超时，5 条结果最坏 30 秒以上；引擎链里第二位的 Google 已经死了。

因此决定：两个工具都改成**纯 Node、纯 HTTP**，删除 puppeteer 通道与 Python 脚本，作为托管提取不可用时的最后兜底。

## 与 ADR 0004 的关系

[0004](0004-hosted-web-extraction-over-self-hosted-fetch.md) 的结论是「网页读取走供应商托管提取，不自建抓取」。它约束的是**新增的** `exa_webfetch` / `parallel_webfetch`：在同样需要「读网页」这件事上，托管提取质量更高，所以新工具不复刻本地抓取。

0005 不推翻 0004，而是补上它没有覆盖的部分：`website` 这个**既有**工具必须本地工作（它的全部意义就是不依赖第三方）。0004 里「不做本地抓取」的成本核算针对的是「新增一条要维护的抓取链路」，而现在这条链路已经存在，只是实现得又重又坏；把它换成 HTTP 只会减少维护面。

## 实测：HTTP 与 puppeteer 的分工

2026-10-21，22 个目标，两条路都用同一个 HTML→Markdown 转换器（纯文本字符数与耗时，逐目标明细见 `.scratch/local-web-tools/spec.md`）：

| 目标 | HTTP | Puppeteer | HTTP 耗时 | Pup 耗时 |
| --- | --- | --- | --- | --- |
| MDN 文档 | 17031 | 17021 | 1028ms | 2497ms |
| 维基百科 | 31964 | 32233 | 1380ms | 3091ms |
| Node 文档 | 115983 | 115946 | 528ms | 4195ms |
| HN 首页 | 4064 | 4064 | 1436ms | 1728ms |
| solidot | 11585 | 11548 | 549ms | 1395ms |
| 豆瓣首页 | 4037 | 4294 | 296ms | 1312ms |
| CSDN 文章 | 11473 | 10189 | 695ms | 2909ms |
| 简书文章 | 2815 | 3262 | 1294ms | 3422ms |
| react.dev | 9000 | 9045 | 602ms | 2383ms |

| 类别 | 结果 |
| --- | --- |
| 正文/文档页（上表九个） | 两条路**等价**，字符数差异多在 ±10%，HTTP 常常略多；HTTP 中位 0.6s，puppeteer 2.9s（冷启动另加 217ms） |
| GitHub 仓库、B 站视频、掘金/淘宝首页 | puppeteer 明显更多，但多出来的是**文件列表、评论、分类导航**，不是正文 |
| 小红书、X | puppeteer 多出来的全是**登录弹窗/登录墙**文案 |
| 知乎（问题与专栏）、Reddit | 两条路都 403；puppeteer 也拿不到 |
| PDF | HTTP 拿到二进制（需按 content-type 拦掉），puppeteer 30 秒导航超时 |

**复现口径**：两条通道的 HTML 都过同一个 `convertHTMLToMarkdown`，再按同一套规则压成**纯文本**计字符数——不要直接量 Markdown 长度，Reddit 的 403 页曾因内联 base64 图被算成 87900 字符，「壳」会被当成正文（实现阶段又踩了一次，所以 `fetchLocalPage` 出口现在会滤掉 `data:` 图片）。HTTP 侧是一次普通 GET + 该转换器；puppeteer 侧是本机 Edge headless + `waitUntil: 'networkidle0'`，冷启动单独计时。

**样本局限**：单机单 IP，以中英文主流站为主。纯客户端渲染且无 SSR 的内容站理论上会让 HTTP 拿不到正文；这批样本里没有出现——出现的「只有 JS 能读」全是登录墙。

## 考虑过的替代方案

- **HTTP 优先、正文过短时自动回退 puppeteer**：否。按「纯文本 < 200 字符」这个阈值，本样本里只有登录墙会触发回退，触发了也读不到东西；代价是保留整条浏览器链路与那条慢路径。
- **保留 puppeteer，只修 bug（别关共享实例、别改全局 headless、加超时）**：否。修完仍然是 2–5 秒一页、需要 Chromium，而正文覆盖并不比 HTTP 更好。只有「读列表页/评论区」是刚需时才值得。
- **保留 Python 搜索后端，只把串行改并发**：否。依赖门槛才是开箱即用的最大障碍（本机实测就卡在这里），而且这层完全没法进 CI 测试。
- **搜索继续带 Google**：否，三条路都死了。`googlesearch-python` 1.3.0 在三种参数组合下都返回 0 条；直连 `/search` 拿到的是「如果您在几秒钟内没有被重定向」的 JS 跳转页，`gbv=1` / `udm=14` 同样 0 个结果节点；puppeteer 打开也是 0 条。
- **搜索保留搜狗**：否。结果链接是 `/link?url=` 跳转，要多发一次请求解析；中文结果与百度高度重叠。
- **自己写一个精简的 HTML→Markdown**：否。选型就是用 opencode 的转换器跑完 22 个目标才定的，重写等于把它的边角（嵌套列表、表格、`details`、链接里套代码）再踩一遍。代价是一个纯 JS 依赖 `htmlparser2`。

## 已知约束

- **不做反爬**：没有 cookie 池、代理轮换、UA/指纹伪装、验证码、TLS 指纹。工具名里的「无反爬」是承诺，不是未完成项。
- **不做 JS 渲染**：删掉 puppeteer 之后，纯客户端渲染的站点读不到就是读不到。这是明确取舍，不是回归。
- **内联 `data:` 图片不进正文**：转换器忠实地输出 `![](data:image/svg+xml;base64,…)`，但模型读不了 base64，而实测 `opencode.ai/zh` 的转换结果 61% 是内联 logo、`cn.bing.com` 41%——留着等于把正文挤出 20000 字符的窗口。过滤放在 `fetchLocalPage` 出口，转换器保持与上游一致。
- **私网地址一律拒绝**：loopback、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`100.64/10`、`0.0.0.0/8`，IPv6 的 `::`、`::1`、`64:ff9b:1::/48`、`fc00::/7`、`fe80::/10`、`fec0::/10`、`ff00::/8`；IPv4-mapped 的 `::ffff:7f00:1` 这类要先还原成 v4 再判（只查 v6 段时它不命中任何一条，等于把 v4 私网全部放行）。域名解析后判定，每一跳重定向重新校验。tool arguments 由模型给、结果会发到群里，而 `http://127.0.0.1:6099` 就是 Yunzai 自己的管理面板。代价是「读自家路由器/NAS」不再支持。
- **一次搜索最多 20 秒**：引擎轮询与抓正文共用一个 deadline，每个请求只拿到「剩余时间」。这是硬上限，不是平均值——上面批评旧实现「最坏 30 秒以上」，新实现不能只是把它换个数字。
- 解析发生在请求之前、与 fetch 自己的解析是两次，**挡不住 DNS rebinding**；它挡的是「模型随手填一个内网地址」。
- 搜索引擎的解析依赖对方页面结构，对方改版就会失效。失败时逐条给出引擎名与原因，不做静默降级。
