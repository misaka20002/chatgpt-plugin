# 记忆召回新增显式「按权重导入」模式

状态：已采纳（2026-10-23）。需求与决策过程见 `.scratch/memory-review-fix/spec.md`。

记忆召回原有两种模式：`memoryRecallProvider` 选「不使用 LLM 判断」时走中文 bigram 相关性匹配，选了 provider 则额外发一次子模型请求挑候选。8cce455 还带过第三种「自动全量」：当 `memoryContextLimit >= maxMemoriesPerUser` 时跳过所有筛选、把可访问记忆全部注入（最多 250 条 ≈ 15 万字符）。那个分支在 2026-10-23 被删除，理由是不可控——用户只是把条数上限调大，就意外得到一份塞满上下文的注入，既没有 LLM 判断也不受条数约束。

删掉之后出现一个新缺口：**没有可用模型、或不想为召回多付一次请求时，没有任何办法把上下文"填满"**。bigram 只注入与当前问题相关的条目，短问题常常只召回三五条；而有些场景需要的恰恰是"稳定、可预期、不依赖模型质量"的一份背景。

因此决定新增一个显式选项 `memoryRecallProvider = 'all'`（锅巴「按权重导入」）。配置值仍叫 `all`、文件名也沿用 `all-mode`：它表达的是"全部候选都参与排序"，与面板上的显示名不是同一层概念。

## 决定

- **配比**：个人记忆（该主体的 `user` + 本群 `user_group`）与群公共记忆（本群 `group`）按**约** 9 : 1 分配 `memoryContextLimit`；群公共条数取 `max(1, round(limit × 0.1))`，上限为群池实际条数。因为下限是 1，`limit=8` 与 `limit=5` 时实际是 1 条（7:1 / 4:1），比例随上限变小而自然偏离。
- **补位**：任一侧不足时由另一侧补满；两侧合计仍不足时注入全部；群池为空则全用个人。
- **不筛选**：不筛相关度、不调任何模型。该模式从一开始就不看 `memoryMinImportance`（该键已于 2026-10-24 整体删除，对本模式没有行为变化）；排序复用 bigram 路径的 `score()`（相关度×10 + 重要性×3 + 置信度×2 + 状态 + 作用域），并以 `updatedAt`、`id` 做稳定次序。
- **不做常驻画像特殊占位**：姓名/称呼等只是个人池里重要性较高的普通条目，无条件占位会挤掉群公共名额、破坏 9:1。
- **权限不变**：两个池都来自既有的 `listRecallCandidates(subjectId, groupId)`，永远不包含其他群友的记忆。
- **配置面**：`'all'` 是哨兵值，必须在 provider 引用校验里像 `'current'` 一样豁免，否则配置加载会把它当成"不存在的提供商"直接抛错。

## 与已删除的「自动全量」的区别

| | 自动全量（已删除） | 按权重导入（本 ADR） |
| --- | --- | --- |
| 触发 | `limit >= maxMemoriesPerUser` 时自动生效 | 用户在「记忆召回判断模型」里显式选择 |
| 条数 | 注入全部可访问记忆，可远超 `memoryContextLimit` | 严格 ≤ `memoryContextLimit` |
| 来源配比 | 无，按重要性混排 | 个人 : 群公共 = 9 : 1，群公共至少 1 条 |
| 可观测 | 无（用户不知道自己触发了它） | 面板选项 + `#记忆统计` 显示当前模式 |

## 后果

- 该模式可能注入与当前话题无关的记忆（这是"填满"的定义），锅巴文案已写明。
- `memoryMinImportance` 已整体删除（2026-10-24），"该模式下阈值失效"这个例外不复存在；`importance` 仍作为 `score()` 的 ×3 权重影响排序，但不再淘汰任何条目。
- 上下文体量由 `memoryContextLimit` 决定，推荐 20 条以内；锅巴最小值提到 **5**，避免出现"1 条上限时群公共占满唯一名额"这类反直觉配置。**这只约束面板新输入**：已存在的 1–4 不会被改写（本仓不覆盖磁盘配置），那种配置下群公共确实会占满名额。
- 若以后要"个人占比可调"，需要新增独立配置项，而不是继续扩展哨兵值——哨兵值只表达模式，不承载参数。
