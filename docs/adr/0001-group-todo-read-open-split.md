# 群待办读写拆分：读取按只读公开信息放开，写入留在群管档

背景：群待办的四个操作最初共用一个工具、统一收在主人/群管档（Bot 闸 + 提问者闸），普通群友连「查看列表」都被拒——而列表属于只读公开信息，群内本来就人人可见，是归错了档位。决定：拆成两个独立工具、分开注册——读取工具按「群聊 + 配置开启」注入，不设 Bot 闸与提问者闸（对齐群公告，Bot 不是群管的群里也能读）；写入工具（设置/完成/取消）留在群管档，注入与自查维持原样。两个工具共用同一个配置键 `GroupTodo`，不新增配置项、不做迁移；guoba 面板结构不变。

**状态（2026-10-19）**：不实施（superseded）。群待办已记为 `wontfix`（见 [`.out-of-scope/group-todo-tools.md`](../../.out-of-scope/group-todo-tools.md)）——本决策唯一目的是把「读取」从群管档放开，而协议端未实现 `get_group_todo_list`，读取面不存在，拆分失去管辖对象。原文与「考虑过的替代方案」保留：其中「Bot 闸在注册层、工具内自查只管上下文与提问者」的分层原则对其余群工具仍有效。将来若协议端支持读取，权限分档需重新决策，不要直接沿用本文结论。

## 考虑过的替代方案

- **保持单一工具、只放开提问者闸**：一个工具只有一份注入条件——写入仍需 Bot 闸，读取就会连带被挡在 Bot 非群管的群外；被否决。
- **单一工具移出 Bot 闸、写入时在工具内查 Bot 角色**：会打破「Bot 闸在注册层、工具内自查只管上下文与提问者」的既有分工，且写入前多一次成员信息查询；被否决。

## 已知约束

- 读取能否真正调通取决于协议端是否实现 `get_group_todo_list`，各协议端支持不一致；不支持时按仓库既有失败语义如实报错，不做特性探测。
