# 贴表情的准入边界：情绪池只收语义自明的脸，物件/动作走点名目录

状态：已采纳（2026-10-26）。需求与决策见 [`.scratch/emoji-like-catalog/spec.md`](../../.scratch/emoji-like-catalog/spec.md)。

`emojiLike` 是「给某条消息贴 QQ 表情回应」的工具，模型报一个情绪，工具在同情绪的表情池里随机挑一张。上线时池子是从别处抄来的一组 face id，没人核对过语义：`惊恐` 在 `angry`、`发呆` 在 `surprised`、`撇嘴`/`魔鬼笑` 在 `scared`（而真正该用的 `发抖`、`吓` 空着）、`猪头`/`变形`/`戳一戳` 在 `speechless`、`牛气冲天`/`大展宏兔` 在 `awkward`。贴出去的情绪经常和键名对不上，而且模型只有 16 种情绪可说，`玫瑰`、`蛋糕`、`咖啡` 这类物件根本贴不出来。

现在按一条标准重建：**语义和键名对得上，贴出去别人一眼能读出这个情绪**。情绪键一个不加（仍是 16 个），另开一个 12 项的具体表情目录给模型点名。

## 考虑过的替代方案

- **只扩池、不加参数**：改动最小、token 不变，但模型仍只有 16 种表达，物件类（玫瑰/蛋糕/咖啡/烟花）永远没有归属。
- **用表情名替换情绪键**：表达最自由，但丢掉「同情绪随机换脸」——那正是回应不像模板的原因；且枚举会膨胀到 299 个名字，每次请求都要付。
- **`face` 用自由文本 + 模糊匹配**：要自己维护匹配规则，模型编名字时只能报错或猜；12 个名字不值得为它引入一层模糊匹配。
- **把节日/生肖/联动/皮肤包也收进池**：`龙年快乐`、`大展宏兔`、`王者召唤` 语义绑时间或 IP，贴上群容易让人莫名其妙；`汪汪`/`企鹅` 系列是角色表情，情绪要连角色一起读。这正是「模糊不清就别硬塞」的落点。
- **允许 Unicode emoji 码点**：速查表明确写了，码点填进 `set_msg_emoji_like` 接口返回 ok、客户端贴出来是空白——静默失败比报错更难查，一律不收。

## 已知约束

- **enum 是每次请求的固定成本**：`face` 目录封顶 12 个是 token 决定，不是语义决定。`emojiLike` 的 schema 因此从 107 → 213 tokens（`test/toolContextAudit.md` 已重跑）。想加名字先问：它是不是某个 emotion 已经能表达的？
- **`emotion` 与 `face` 都是可选的**，`required` 为空，至少给一个由 `func` 自查。这样「只想贴一朵玫瑰」不必被迫编一个情绪；代价是模型两个都不给时要多一轮纠错。
- **名字写错不吞掉，也不白耗一轮**：`face` 不在目录但 `emotion` 合法 → 继续贴，并在工具返回里写明回落；两条都不成立才 `Error: …`。
- **id 有效性只能靠来源表**：`set_msg_emoji_like` 对无效 id 也返回 ok、客户端空白，本地没有校验手段。准入只从 [QQ 表情 ID 速查器](https://52-moyna.github.io/maibot_plugin-Response/face-lookup.html)（用户确认其 id 均已验证）里取，上线后用 `get_emoji_likes` 抽查。
- **枚举与映射是两份字面量**：schema 里保持字面量数组，`toolContextAudit` 才能静态求出 token 数；脱节风险由 `test/emojiLikeTool.test.js` 逐个真跑枚举兜住。
- **`utils/face.js` 的两张表只追加不改名**：`181` 在仓库叫「骚扰」、速查表叫「戳一戳」，改名会动到 `[表情名]` 输入匹配与既有日志。同名冲突（`450 撇嘴` vs `1 撇嘴`）在反向表保留原有映射，正向表按 id 各记一条。
