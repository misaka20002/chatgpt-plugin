# 女娲蒸馏做成主人指令，而不是 agent 工具

状态：已采纳（2026-10-30）。需求与实现范围见 `.scratch/nuwa-distill-command/spec.md`。

群友 Skill 蒸馏是一段重任务：读本群样本、脱敏、按 50k 一块切分、逐块调子模型、合成、自检、打包。它原来以 agent 工具 `generateGroupMemberSkill` 的形态存在——主人在智能模式里说一句「蒸馏一下 @某人」，模型自行决定调用并填 `target_id`。

问题出在「谁来决定目标」和「谁来解释代价」这两件事上。目标只能来自服务端事件：@ 段、引用消息的发送者、QQ 号，都在 `e` 里，而模型看到的只是文本，它得先把 @ 转成数字再回填。代价也只能写在工具的 `description` 里，由模型转述——而一次蒸馏要花几万 token、几分钟，主人需要在花之前看到准确数字，不是模型的复述。工具的 schema 还会常驻每一次对话的上下文，可这条能力一个月用不了几次。

## 备选方案

1. **保持工具**：继续让模型调用，只把锅巴开关挪到记忆设置区。改动最小，但解析与代价告知仍然交给模型。
2. **工具与指令并存**：智能模式里能调，指令也能触发。两条入口要同时维护，且模型仍可能在主人只想聊天时自己发起一次昂贵的蒸馏。
3. **改为主人指令 + 确认门**：`#女娲蒸馏` 由框架匹配，服务端解析目标，先发说明与注意事项，主人回 `Y` 才开跑。

## 决定

选 **3**。原因：

- **解析归服务端**：@ / 引用 / QQ 号都从事件里取，错了当场回用法提示，不会先烧掉几万 token 才发现目标错了。
- **确认门是唯一能讲清代价的位置**：目标、实际使用的提供商、样本来源与上限、token 预算、块数、预计时长、产物投递位置，都能在开跑前一次性说清；而且这条消息不受模型改写。
- **上下文成本归零**：工具 schema 从每次请求里消失。这条能力本来就只对主人开放，不值得为它付常驻成本。
- **身份闸由框架保证**：`permission: 'master'` 在注册期生效，比工具里靠 `e.isMaster` 自查更早一层。

## 后果

- **代价**：主人必须记住一条指令，不能再靠「说一句话让它自己看着办」。这是有意的取舍——一次几分钟、数万 token 的操作，值得多打四个字。
- **代价**：原来的「生成完让模型点评这份 SKILL.md」环节没有了。摘要改由确定性数据拼出（样本条数、置信度、心智模型数量、自检结果、产物目录），不再有模型的即兴评价。
- **边界**：只在群聊可用、只处理当前群的一名成员、只读本群 `user_group` 事实与本地原文。跨群与群公共事实仍不参与（见 [ADR 0012](0012-group-skill-facts-as-background.md)）。
- **可逆性**：如果将来要回到模型调用，应当新增一个薄工具去复用 `utils/groupMemberSkillRun.js`，而不是把编排逻辑搬回 `func` 里——编排与入口已经分离，两种形态可以共存于同一段逻辑之上。
