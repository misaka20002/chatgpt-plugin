# 记忆召回与夜间提炼：配置即上限，去掉隐式截断

Status: done

Feature: `memory-review-fix`（`8cce455` 评审结论的落地）
Decision date: 2026-10-23

## 背景与基线（决策依据，已核实）

- **实时召回**：每轮对话由 `apps/chat.js` 调记忆召回模块，注入格式为「定位 JSON + 正文 + 作用域标签」，定位 JSON（scope/subjectId/factKey/factValue）约 100 字符，是为了让 `Memory_Tool` 能精确撤回；正文单条硬上限 500 字（超长拒写）。
- **8cce455 之前**：召回恒走 bigram → 注入恒被 1500 字截断，`memoryContextLimit` 设 8/50/100 都一样；提炼提示词里没有历史段。
- **8cce455 引入的两处行为**：① `memoryContextLimit >= maxMemoriesPerUser` 时跳过筛选、注入全部可访问记忆（最多 250 条 ≈ 15 万字符）；② 提炼每片追加最多 8000 字符「历史记忆对照」，但切片时没给它留预算。
- 实测口径：每条约 132 字符（正文 20 字）／172（60 字）／612（500 字）≈ 49／82／449 token。

## Problem Statement

我按自己的需要把「对话记忆数量限制」设成 50 或 100，本意是让 Bot 多用一些记忆，但实际注入的正文永远被 1500 字砍掉，配置形同虚设；而一旦把它设到不小于「单用户最大记忆数量」，系统又反过来把库里所有可访问记忆一次性塞进来，条数和长度同时失控。两种结果都不是我配置时想要的。

同时，凌晨提炼把「历史记忆对照」塞进已经按预算切满的分片，配置若贴着模型上限填，整片请求会超上下文、整窗提炼失败；记忆状态里也看不到群公共容量和「超 95% 整理至 70%」的规则。

## Solution

让「对话记忆数量限制」成为唯一且真实生效的条数上限：设多少条就最多注入多少条，正文不再被字符截断；删除「达到个人上限就全量注入」这个特殊模式。提炼分片预算放宽到 50000，历史对照保留但明确它是写入侧去重参考。状态展示补齐两个容量与整理阈值。评审提出的文档、注释与代码整洁问题一并收口。

## User Stories

1. 作为 Bot 主人，我想让「对话记忆数量限制」真正决定每次注入的条数上限，这样我调配置就能控制对话上下文的体量。
2. 作为 Bot 主人，我不想注入正文被 1500 字悄悄截断，这样我把上限设成 50 条时不会被砍成十来条。
3. 作为 Bot 主人，我不想因为把对话上限设到不小于个人容量就触发"全量注入"，这样我的配置不会产生意料之外的大段上下文。
4. 作为 Bot 主人，我想在锅巴里看到"推荐 20 条以内"的填写建议，这样我知道这个值填多少合理。
5. 作为 Bot 主人，我想知道"设 20 条"是上限而不是强制条数，这样我不会误以为无关记忆会被硬塞进来。
6. 作为群成员，我想只看到与当前问题相关的记忆，这样注入不会浪费在无关事实上。
7. 作为维护者，我想记住"设 20 条不等于每次注入 20 条"这一语义，这样以后不会有人把相关性过滤当成 bug 修掉。
8. 作为维护者，我想凌晨提炼的分片预算是 50000，这样片数不会因为 30000 偏小而虚高。
9. 作为群成员，我想当天聊天里的"改口"能立刻覆盖旧事实，而不是让库里并存两条互相矛盾的记忆。
10. 作为维护者，我想「历史记忆对照」继续保留在提炼请求里，这样跨键同义事实不会重复新增，也把 >95% 压缩的压力留在写入侧。
11. 作为 Bot 主人，我想在 `#群记忆状态` 看到个人与群公共两个容量上限以及 95%→70% 的整理阈值，这样我知道什么时候会触发夜间整理。
12. 作为 Bot 主人，我想 `#记忆统计` 与 `#群记忆状态` 用同一份容量说明，这样两个指令不会说法打架。
13. 作为维护者，我想压缩时"跨键同文本"合并保持现状（用户已接受被合并项的槽位随之消失），这样压缩达标率不受影响，但注释必须如实描述这一取舍。
14. 作为维护者，我想注释与文档不再宣称"不能让模型任意合并"这种与代码相反的话，这样下次评审不会把旧措辞当新问题抓出来。
15. 作为维护者，我想坏证据 JSON 不再被空 catch 静默吞掉，这样统计失真时我能看到一条带条数的告警。
16. 作为维护者，我想锁租约统一写成 `EX`，这样排查锁时长时不用在秒与毫秒之间换算。
17. 作为维护者，我想容量统计与"过滤+排序"各只有一份实现，这样改规则时不会漏掉另一处。
18. 作为维护者，我想压缩预算的判定函数名能读出"这一片装不装得下"，这样不必逐行推导。

## Implementation Decisions

**召回注入（记忆召回模块）**

- 删除「全量注入」分支：`memoryContextLimit >= maxMemoriesPerUser` 不再跳过排序与 LLM 选择，也不再注入全部可访问记忆。
- 取消注入文本的字符截断：组装函数不再接受 `maxChars`，只负责拼行与"不可信数据"标注；长度由条数上限与单条 500 字共同约束。
- `memoryContextLimit` 是条数上限：bigram 只取相关项、LLM 只选相关项，因此"设 20 条"是上限而非配额。该性质在 LLM 选择路径原本成立（`Math.min(2, limit)`），但 **bigram 路径的常驻画像曾绕过 limit**（先无条件 `slice(0, 2)` 入队，`memoryContextLimit=1` 时实际注入 2 条）；本轮一并修正为 `Math.min(2, limit)`，删掉全量注入分支后它就是无例外的不变式。
- 锅巴「对话记忆数量限制」文案：删掉全量模式与 `maxMemoriesPerUser` 门槛描述，改为"每次对话最多注入的记忆条数，推荐 20 条以内（更长会挤占对话上下文）"。

**提炼分片预算（每日提炼）**

- 提炼与压缩的输入预算**共用同一个常量** `MEMORY_INPUT_TOKEN_LIMIT = 50000`（定义在 `extractor.js`，压缩直接 import，不做第二份定义）：锅巴没有该字段，磁盘上残留的旧值（30000）不应继续生效，`memoryGroupCapture.inputTokenLimit` 键删除。
- 「历史记忆对照」保留：每片最多 8000 字符，按与本片发言的相关度优先取舍；不从分片预算中扣减（约占 50K 的 13%）。
- 压缩**不预留输出 token**：决策 JSON 只是保住/合并/归档的 ID 列表，长度由输入条数决定，不是另一份等量正文。
- 临时事件保留期**保留 `memoryGroupCapture.eventRetentionDays` 配置**（默认 90 天），不改成常量、也不与 `rawRetentionDays` 合并：它管的是 `episode`/`plan` 未给 `validTo` 时的默认有效期，与"原文留几天"是两件事。锅巴 schema 里该字段保持注释状态（面板不暴露），仅保留配置键以便下次调整时能找到。
- 锅巴文案**不写**"应明显小于模型上下文"这类提醒。

**压缩合并语义（记忆存储层）**

- 保持现状：`kind` 与正文（去空白后）相同即视为同一原子事实，迁移证据并归档被合并项。
- 明确接受：被合并项的 `factKey/factValue` 随之消失，之后按该槽位撤回不再命中。该取舍写进文档的已知限制。
- 代码注释改为如实描述；不在本轮引入槽位别名或继承。

**状态可见性（记忆管理指令）**

- 抽一份共用容量说明：个人上限 / 群公共上限 /「有效条数严格超过 95% 时夜间整理至 70%」。
- `#记忆统计` 与 `#群记忆状态` 都引用同一份，避免文案漂移。

**越界项保留**

- 合并证据时给外部群补 GRP 反向索引（与单条写入一致，供按群清理反查）；注释写明它不参与召回、不改变权限。
- 术语表的「记忆容量目标」「临时超额记忆」保留。

**代码整洁**

- 去掉容量统计的纯转发方法，只保留一个公开实现。
- 收敛两处重复：候选形状校验 + 归属推导、有效项过滤 + 按 id 排序，各保留一份实现，供加锁前后与扫描/提交共用。
- 重命名压缩预算的两个内部函数：一个表示"为本片决策 JSON 预留的输出 token"，一个表示"这一片能否装进一次请求"。
- `(scope, ownerId, groupId)` 参数对象化**不做**。

**错误可观测性**

- 证据 JSON 解析失败不再空 catch：跳过该条并计数，循环结束统一 warn（证据统计与证据迁移两处）。

**锁租约**

- 作用域锁统一为 `{ NX: true, EX: 120 }`。

**文档同步**

- 记忆专题文档：压缩"额外发一次 POST"改为"创建一次任务、每片一次 POST"；召回条目补"LLM 选择、全量模式已删除、正文不截断"；补"跨键合并后撤回按保留项的键"。
- 设计与计划记录：删掉"独立一 POST"、">110000 字符跳过"、"尚未实施"等过期表述；作废"50/50、100/100 全量导入"的验收条目。

## Testing Decisions

**好测试的标准**：只断言对外可观察行为——注入文本里出现了哪些条目、条数上限、请求是否发出与发出几次、状态文案包含哪些字段、配置读写结果；不断言内部函数名，不锁定与决策无关的具体字符数（唯一例外是 8000 这类契约常量）。

**复用现有 seam，不新增**：

1. 召回：`buildMemoryPrompt(e, query, { store, config, llm })`——注入假 store 与假 llm（现有召回用例均走这里）。
2. 提炼：`runExtraction({ rows, ctx, evidenceMap, cfg, llm, historyLoader })`——注入 llm 捕获 prompt 断言内容与片数。
3. 夜间任务：`DailyConsolidation.runDaily({ llm, compressionLLM })`。
4. 指令：直接调用处理函数并传假 `e`（现有指令用例的做法）。
5. 配置：锅巴 schema 的读写与文案断言（现有配置用例的做法）。

**要覆盖的行为**：

- 上限 100 条 + 个人容量 100（旧版触发全量注入的配置）：注入条数仍 ≤100，不再是全部可访问记忆——**这是本轮唯一新增的条数断言**。
- 上限 20 条 + 个人容量 100：注入条数 ≤20 且无关记忆不出现——这是**既有行为**，删除全量分支后作为回归守护保留（bigram 与 LLM 两条路径的 ≤limit 已有同类用例）。
- 正文 1700 字的长记忆：完整出现在注入文本中（旧版会被 1500 截断）。
- 提炼默认分片预算 = 常量 50000；历史对照仍在 prompt 中且 ≤8000 字符。
- 两个状态指令都包含个人上限、群公共上限与 95%→70%。
- 锅巴「对话记忆数量限制」文案包含"20 条"、不再包含"全部注入"。
- 保持通过：压缩合并的现有用例（语义未变）、<95% 不发压缩 POST 的用例。

**先例**：`test/memoryV2.test.js` 的召回与提炼用例、`test/memoryApps.test.mjs` 的指令用例、`test/providerConfig.test.js` 的锅巴用例。

## Out of Scope

- 跨键合并的槽位别名/继承（真无损方案）——单开议题，需要存储模型层面的 ADR。
- `(scope, ownerId, groupId)` 参数对象化。
- 已保存配置的迁移（旧配置里的 inputTokenLimit 已完全不生效）。
- 真实 Redis / 真实模型链路的验收（部署后看日志）。
- 群公共容量是否参与召回门槛（全量模式已删除，该问题消失）。

## Further Notes

- 决策来源：`8cce455` 的两轴评审（Standards 10 项 / Spec 7 项）+ 2026-10-23 与用户逐项拍板；被否的上一版实现（8000 字上限、跨键合并降级为容量归档）在本轮均不采纳。
- 已知取舍：注入长度现在完全由用户配置决定，超配会挤占对话上下文，只靠锅巴文案引导，不再有代码兜底。
- 不变式：实时写入允许暂时超额；不得恢复按分数的物理淘汰；<95% 不得新增压缩 POST；模型输出一律经服务端可信 ID + 快照校验；`manual` 不得归档或合并删除；不得跨主体/跨群/跨作用域合并。
- 输入长度边界：本模块认可的"限制输出长度"= 条数上限 + 单条正文 500 字，不再叠加字符级截断。

## 2026-10-23 追加：记忆召回「按权重导入」模式

**需求**：在「记忆召回判断模型」下拉里新增一项「按权重导入」。选中后**不调用任何模型**，用该成员的个人记忆与本群公共记忆把 `对话记忆数量限制` 填满，个人 : 群公共 ≈ 9 : 1，群公共至少 1 条。

**决策**

1. 配比：`groupTarget = max(1, round(limit × 0.1))`（上限为群池实际条数），`personalTarget = limit - groupTarget`；任一侧不足由另一侧补满，两侧合计仍不足则注入全部；群池为空全用个人。
2. 池的边界：个人池 = 该主体 `user` + 本群 `user_group`，群池 = 本群 `group`，都来自既有的 `listRecallCandidates`，**不含任何其他群友的记忆**，权限链路不改。
3. 排序复用 `score()`（相关度×10 + 重要性×3 + 置信度×2 + 状态 + 作用域），`updatedAt`/`id` 做稳定次序。
4. 常驻画像**不做**特殊占位：填满模式下按分数自然入选，占位会挤掉群公共名额、破坏 9:1。
5. 哨兵值 `'all'`；`providerProfiles.js` 的引用校验必须像 `'current'` 一样豁免，否则加载即抛"引用的模型提供商不存在"。
6. 锅巴：选项插在「不使用 LLM 判断（仅文字匹配）」的下一格，文案注明"≈9:1 填满上限，可能含无关记忆"；`对话记忆数量限制` 最小值由 1 改为 **5**（消除 limit=1 时群公共占满唯一名额的反直觉配置）。
7. 不新增日志：该模式只取调用方**本就授权可见**的候选——主人 @他人 时包含对方跨群 `user`（既有权限），普通成员 @他人 只有 `user_group`；不存在越权填入他人记忆的路径，因此不需要 info 级记录。
8. 与已删除的「自动全量」区别（写进 ADR 0006）：显式选择、严格受 `memoryContextLimit` 约束、有来源配比、面板可见。

**验收**

- `''` → 仅相关条目；`'all'` → 恰好 `limit` 条（候选足够时），个人 18 / 群公共 2（limit=20），不调用模型。
- 群公共仅 1 条 → 19 + 1；无群公共 → 全个人；个人只有 3 条且无群公共 → 注入 3 条不报错；**反方向**：个人 5 条 + 群公共 30 条 → 5 + 15。
- @他人权限不变：主人 @他人 时 `'all'` 可取对方跨群 `user`，普通成员只取对方 `user_group`。
- 锅巴选项值顺序 `['', 'all', 'current', ...providerIds]`；`min` = 5；`'all'` 能保存且能通过加载校验；`#记忆统计` 显示当前召回模式。

**验证**：`npm run test:memory` 131/131；`npm run check` 通过。

## 2026-10-24 追加：删除 `memoryMinImportance`，统一排序器

**需求**：文字匹配现在很难匹到记忆，阈值只会进一步砍掉已匹配的条目；移除该配置，文字匹配到的全部参与排序，超过 `最大对话记忆数量` 时按 `score()` 取前 N。

**决策**

1. 删除 `memoryMinImportance` 全链路：`config.js` 默认键与 `1–10 → 0–1` 旧值归一化、`chat.js` 传参、锅巴字段、`#记忆统计` 的"对话最低重要性"行、`rankMemories` 的 `options.minImportance` 参数。磁盘上的死键由既有的 `removeExtraKeys` 在加载时剔除，不主动改写文件。
2. bigram 路径的入选条件只剩 `rel > 0`（文字上有命中）；命中后不再设重要性门槛，全部交给 `score()` 排序再按 `limit` 截断。
3. 常驻画像（姓名/称呼等，≤2 条）继续无条件注入并计入上限——阈值删除不影响它。
4. 排序口径统一：新增内部 `rankByScore(list, queryTokens, { requireHit })`，"算一次分 → 排序"只此一处；`rankMemories`（`requireHit: true`）与按权重导入的 `selectAllByRatio`（不要求命中）共用。
5. `utils/userMemory.js` 的 `minImportance` 是遗留 Hash 路径的独立参数，与本配置无关，不动。

**验收**

- 低重要性（0.05）但文字命中的记忆会被注入（旧 0.4 阈值会整条砍掉）。
