# 角色动图：保留所有动效，优化辅助 LLM 的动作选择提示词

Status: done

## 任务与观察

用户反馈：QQ群的角色动图字幕显示「你在叫派蒙吗？是新的海鲜品种吗？」相关短句，动图 3 秒，视觉上全程似乎只有普通表情；锅巴「表情渐变过渡」已开；约 1.5 秒后有不美观的横向抖动。用户经过第一轮访谈**拒绝一刀切禁用横向抖动**，希望保留 idle 自然轻摆和所有既有动作，最终选定仅通过更明确的提示词引导辅助 LLM 选中已有的 idle，不增加新动作。

**证据边界**：提供的是聊天截图，不是原始 GIF，也没有该轮辅助模型的 `expressionId` 和 `action`。截图不能证明整个 GIF 没有命中特色表情，也不能证明动作恰好在 1.5 秒才启动。

## 仓库与已证实的代码事实（2026-10-26）

- ARM `arm-cc` 仓库 `v2` 已安全快进 `1ffd781` → `1b2dd54da84939dc78b8e35b961c76ccbd72a35b`；未修改动图功能代码。
- `utils/avatar/config.js`：辅助模型返回的 `action` 和 `expressionId` 相互独立。即使 `expressionId: null`，也可以返回合法的 `shake`、`wobble`、`headshake` 等动作；本地失败兜底才使用 `idle + null`。
- `utils/avatar/render.js`：只有 `transition=true` **且实际命中特色表情资源**，才走「正常段 → 350ms 溶解 → 特色段」时间线。未命中时直接调用 `frameParts` 播放普通三帧，但仍按照 `cue.action` 叠加横向反应动作，和渐变开关无关。
- 另外即使 action=idle，资源默认 `swayAmpX=1` 也会叠加细微水平摆动。水平位移使用正弦函数乘以全时长包络 `sin²(πt/duration)`，中点较明显。反应式 `shake`、`wobble`、`headshake` 分别再叠加横移，其中 wobble/headshake 也会旋转。
- 3 秒且命中特色表情时，正常段为 0–1500ms，溶解段 1500–1850ms，特色段反应动作约从 1850ms 起在 200ms 内缓入。**普通表情路径没有“1.5 秒后才开始抖”的计时器**。
- 只读验证：利用真实 `avatarFrame` 构造 `expressions=[]` 资源，在 `t=1500ms` 时默认运动参数所得水平位移：idle 约 +0.97px、shake 约 +4.47px、wobble 约 -7.22px、headshake 约 +7.19px；开关 true/false 数值相同。这是可能原因的代码复现，**不是用户原 GIF 的逐帧结论**。
- `docs/avatar-reply-auto.md` 已指出仅选中特色表情才渐变。原有 `test/avatarReply.test.mjs` 已覆盖特色表情延后反应动作；用户明确拒绝「普通表情 x 必须为零」的约束，因此不增加该类测试。实施前原有 `npm run test:avatar` 已通过（37 + 1）。

## 第一轮用户反馈（已收束，旧推荐不实施）

- **Q1**：用户明确**不希望按普通表情或 `expressionId=null` 一刀切禁用横向抖动**。横向反应动作仍交给 LLM 选择；用户询问是否已有无额外抖动的 `action`，以及能否新增一个小幅度动作。之前「普通表情 GIF 的 x=0」方案取消。
- **Q2**：`idle` 的轻微左右摆动是必须的，像真人；**不允许**将基础 `swayAmpX` 归零。
- **Q3**：保留现有**所有**眨眼、张嘴、呼吸、说话倾斜、上下跳动、点头和各种强烈左右反应动作，不做已有动作的全局禁用或减幅。

## 用户问题的源码结论

- `AVATAR_ACTIONS` **已有 `idle`**；在 **`expressionId=null`** 时 `action='idle'` 没有额外的摇头或快速抖动，但仍有 `swayAmpX` 基础左右微摆、呼吸与轻微倾斜，正是用户希望保留的自然动态。
- **特殊情况**：当 `expressionId` 命中特色表情且 `action='idle'`，`frameParts` 当前会改为执行该特色表情的 `expression.animation`，因此此时 `idle` 不一定意味着无额外反应，不能把它一概宣传为「所有场景绝对不抖动」。
- 实施前 `createAvatarCue` 的提示词**只列动作枚举，没有逐个解释动作语义或「普通语气优先 idle」规则**。本次只增加提示词内容、不增加一次模型请求；此类规则引导但不能保证 LLM 每次都选中指定动作。
- 当前默认基础 `swayAmpX=1`；已有 `wobble` 在此基础上增加幅度默认约 9px，并有约 3° 旋转；`shake` 默认约 3.5px 且频率更快。用户决定**不增加低强度动作**，只改善 LLM 选择现有动作的判断依据。

## 第二轮已确认（Q4～Q6）

- **Q4 = B：不新增动作**。用户认为「轻微摇摆」无法表达疑惑；对于「你在叫派蒙吗？是新的海鲜品种吗？」这类轻松反问，现有 `action: 'idle'` 是最佳选择，不创建 `gentle_wobble`，原 `AVATAR_ACTIONS` 七个动作和运动幅度完全不变。
- **Q5 = A：增强小模型的动作选择指令**。辅助模型为 Gemini 3.5 Flash Lite；需要**清楚写出动作含义、默认选择和避免误用的情况**，而不是只给枚举。普通问句、俏皮反问、轻度困惑、语气平和的玩笑首选 `idle`；仅当文案明确体现强烈情绪或动作意图，才用强烈横向动作；不得仅因为问号、感叹号或「困惑」一词就选 `wobble/shake/headshake`。保持原一次模型请求，不强制代码二次映射。
- **Q6 = A：特色表情自带动画语义不变**。若 `expressionId` 命中特色立绘且 `action='idle'`，继续使用该资源配置的 `expression.animation`；不能在渲染器内新增禁止抖动规则。基础立绘 `idle` 继续保留自然左右微摆。

## 第三轮已确认（Q7～Q8；用户选 B / B）

- **Q7 = B：不加入示例、不写复杂决策树。** 辅助模型当前使用 Gemini 3.5 Flash Lite，用户认为其理解能力足够；只需要简明、清楚地解释七个现有动作的具体含义、语气适用范围以及默认 `idle`，**不要提供示例台词或示例 JSON**，也不需额外引入显式步骤。此选择不否定 Q5 已确认的语义清晰与强动作须有充分理由。
- **Q8 = B：不调整 `expressionId` 的选择引导。** 原提示词中的 `expressionId 只能是输入表情的 id 或 null` 保持原样，不增加「普通问句强制 null」或新的情绪对应规则；不改变特色表情可自带动作的既有约定。
- 因 Q7/Q8 已确认，先前有关「新增轻晃动作」、「全程普通表情水平位置归零」、「根据字幕强制改写模型输出」的方案均**不实施**。

## 最终已实施方案（只修改动作选择的提示词）

**修改点**：仅在 `utils/avatar/config.js:createAvatarCue` 的 `systemPrompt` 中，保留现有电影字幕格式、长度限制、输入不可信内容约束以及 `expressionId` 规则，接在 `action 只能是 ...` 后添加一段清晰但紧凑的自然语言动作释义。

**实际新增的动作选择提示词（没有新增示例或流程步骤）**：

> 动作要符合回复的实际语气，默认优先 idle：自然待机，仍有轻微左右摆动、呼吸和说话，适合普通聊天、轻松提问、俏皮反问、轻微疑惑及日常玩笑。bounce 代表明显开心或兴奋时的上下跳动；shake 代表强烈激动或颤动时的快速左右抖动；wobble 代表夸张困惑或晕眩时的明显左右摇摆；nod 代表明确点头肯定；headshake 代表明确摇头否定；recoil 代表明显受惊的后缩。只有回复确实表达较强情绪或明确动作时才选择非 idle，不要为了活泼强行加动作。不要仅因问号、感叹号或普通疑惑就选择明显的摇晃。

此文案说明动作而非规定动画强度，也**不是任何固定回复与 `idle` 的硬编码映射**。原有七个动作均可选择；原字幕/表情字段不变。由于不调整 `expressionId`，某些被模型选中的特色表情仍可能运行自带摇晃动画，这属于已保留的旧行为，而非保证所有 GIF 都不抖动。

**验收**：
1. 测试可直接断言生成给辅助 LLM 的 `systemPrompt` 覆盖七个现有 action 的含义、默认 idle、普通疑问无需强横抖；不包含示例台词、示例 JSON，也没有约束 `expressionId` 默认为 null 的新增文案。
2. `AVATAR_ACTIONS` 枚举、`expressionId` 选择语义、解析合法性、失败回退、字幕分段/时长/帧率、默认左右轻摆、`render.js` 渐变和特色表情自带动画全部不变。
3. `npm run test:avatar` 和相关测试通过；对辅助 LLM 的动作选择改善属于提示词引导，不承诺 100% 选择 `idle`。
