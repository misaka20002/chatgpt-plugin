# 女娲蒸馏：把群友 Skill 从 agent tool 改为主人指令

Status: done（工作区实现，未提交；2026-10-30）

## Problem Statement

群友 Nuwa Skill 现在是 agent 工具 `generateGroupMemberSkill`：主人在智能模式里说一句「蒸馏一下 @某人」，由模型自行决定调用并填 `target_id`。四个问题：

1. **解析交给模型**：@ 段、QQ 号、卡片里的数字都要模型自己认，认错一次就是几万 token 白烧，而主人看不到它填了什么。
2. **上下文常驻**：工具的 `name` / `description` / `parameters` 每次请求都要发给模型，而这条能力一个月用不了几次。
3. **没有讲代价的位置**：「会花多少 token、要等多久、产物发到哪」只能塞进 `description`，转述给主人时是否走样不可控。
4. **开关放错区**：它依赖记忆采集的授权与原文保留期，开关却挂在「可选工具」区，与真正决定它行为的那组设置分居两处。

另外，本地取样只调 `getRecentRawMessages`（按时间倒序取 20000 条就停），保留期内更早的原文根本没被读过——数据在库里，读不到。

## Solution

删掉工具，改为主人指令 `#女娲蒸馏`。目标取自 @、QQ 号或引用消息；解析在服务端做，不经过模型。

指令先发一份说明与注意事项——目标、实际使用的模型提供商、样本来源、条数上限、token 预算与块数、耗时、隐私边界——主人回 `Y` 才开跑；回其他内容或 180 秒不回复即取消。确认之后才读样本、才调模型。

取样改为分页扫满保留期，再在候选集内按时间等距抽最多 6000 条，覆盖整段时间而不是只取最近一截。

## User Stories

1. 作为 Bot 主人，我想用 `#女娲蒸馏 @某人` 直接开跑，而不是先让模型把我的话翻译成工具参数，这样 @ 错了也不会白烧 token。
2. 作为 Bot 主人，我想用 `#女娲蒸馏 123456789` 指定目标，这样不必先 @ 对方。
3. 作为 Bot 主人，我想引用对方的一条消息再发 `#女娲蒸馏`，这样手边没有 @ 也能指定同一个人。
4. 作为 Bot 主人，我想在花掉几万 token 之前看到这个任务的完整代价（模型、条数、块数、时长、投递位置），这样我能判断现在值不值得跑。
5. 作为 Bot 主人，我想在确认文案里看到实际会用哪个模型提供商，这样账单不会出现在我没预期的接口上。
6. 作为 Bot 主人，我想用一次 `Y` 表示确认、其他任何回复都算取消，这样不需要记额外的命令。
7. 作为 Bot 主人，我想确认窗口有 3 分钟，这样挑目标、看说明时不会被 120 秒掐断。
8. 作为 Bot 主人，我想超时和手动取消给出不同提示，这样我知道是没搭理还是回错了词。
9. 作为 Bot 主人，我想产物默认落到我的私聊，这样别的群成员的聊天节选不会被扩散到群里。
10. 作为 Bot 主人，我想私聊发不出去时自动回退到本群，并在摘要里注明，这样不会静默丢文件。
11. 作为 Bot 主人，我想在同一个群里同时只能跑一个蒸馏任务，这样重复触发不会把两个重任务叠在一起。
12. 作为 Bot 主人，我想在开关关闭、非群聊、目标不是本群成员、样本不足时看到一句明确原因，而不是静默无响应。
13. 作为 Bot 主人，我想在结束时看到样本条数、置信度、心智模型/启发式数量、自检结果、耗时与产物目录，这样不用翻日志就知道这次质量如何。
14. 作为 Bot 主人，我想样本按时间等距抽样，这样同样 15 万 token 能覆盖整个保留期，而不是只覆盖最近十天。
15. 作为 Bot 主人，我想保留期内更早的原文也能被读到，这样存了半年的数据不会因为「只读最近两万条」被浪费。
16. 作为 Bot 主人，我想在文案里看到覆盖范围受哪两个上限约束，这样我能预期产物是「这两年的他」还是「最近的他」。
17. 作为 Bot 主人，我想开关在每次触发时读实时值，确认之后还会复查一次，这样中途关掉能立刻生效。
18. 作为群成员，我不用担心主人误触发把我的心事蒸馏进群里——产物默认走私聊，而且只有主人能发起。
19. 作为维护者，我想命令解析与确认词判定是纯函数，这样它们能被单测覆盖，而不必起宿主环境。
20. 作为维护者，我想编排逻辑离开 `utils/tools/`（那里只放 AbstractTool 子类），这样目录约定不会因为一次形态变更而失真。
21. 作为维护者，我想日志前缀与实际模块一致，这样排查时不会去找一个已经不存在的工具类。
22. 作为维护者，我想工具注册从 `AbstractTool` 列表里彻底消失，这样模型不会在主人只想聊天时自己发起一次昂贵的蒸馏。
23. 作为维护者，我想 `utils/groupMemberSkill.js` 继续保持「无 Config / Redis / 子模型」依赖，这样 `npm run test:nuwa` 仍然能直接跑。

## Implementation Decisions

**形态与入口**

- 指令挂在 `apps/atGraph.js`（与 `#at图谱` 同一个插件类、第二个 rule）：这是需求方的指定，且两者都以「本群记忆采集」为前提。`index.js` 按文件注册（每文件取第一个导出），所以拆两个文件本身不会丢插件——真正的限制是**同一个文件里放两个导出**才会。`name` 保持不变（`checkDisable` 按插件名匹配群级启用/禁用名单，改名会让既有名单失效），只扩 `dsc`。
- 规则 `^#女娲蒸馏`，`permission: 'master'`——身份闸在注册期生效，处理函数不再重复判身份。优先级与 `#at图谱` 同级（500），早于对话入口。
- 只在群聊可用；非群聊直接回一句原因并结束。
- 目标来源有三个：@ 成员、引用消息的发送者、消息里的纯数字，任一即可；**两个来源指向不同的人就拒绝**（确认之后要花十几万 token，不静默择一）。引用 Bot 自己的消息不算目标——那通常只是「带着上文说话」，忽略它也就不会与号码/ @ 冲突。其余拒绝情形：无目标、@ 多个成员、@ 全体、数字格式不合法、@ 到 Bot 自己——一律只回用法，不读样本、不调模型。
- 解析与确认词判定放在纯逻辑模块：`parseDistillTarget({ at, atAll, replyUserId, text, selfId })` 返回 `{ ok: true, targetId }` 或 `{ ok: false, reason }`；`isConfirmWord(text)` 沿用仓库既有口径 `/^(是|y|yes|确定|确认)$/i`。
- 结构化段由既有 `extractStructured` 提供，命令层只负责把 `at` / `atAll` / `reply.userId` 转交给纯函数。

**开关**

- 字段名保持 `enableGroupMemberSkillTool`（改字段名会丢掉已保存的值），标签改为指令口径，说明重写。
- 锅巴位置：`智能模式 记忆设置` 分隔条之后、`启用 AT 图谱` 之后、`允许成员删除自己的记忆` 之前。
- 每次触发读实时值；确认等待结束后再复查一次，关闭则回「开关已关闭，本次取消」。

**确认门**

- 等待窗口 180 秒（`awaitContext(false, 180)`）。宿主的 `setContext` 只在没有 resolve 回调时才用 timeout 文案，而 `awaitContext` 一定设了回调，所以超时以 `false` 兑现——处理函数必须显式判 `!e_new` 并回「确认超时，已取消」。
- 确认词之外的任何回复都回「已取消」。
- 文案定稿（占位符运行期填真实值）：

```
🧬 女娲蒸馏 · 即将开始
目标：{昵称}（{QQ}）
模型：{提供商标签}（当前默认对话提供商）
样本：优先本群记忆采集的原文（当前保留 {N} 天）与已存个人事实；
      不足 30 条时回退扫描本群最近 20000 条消息
      最多取 6000 条，超出时按时间等距抽样
脱敏：QQ、群号、手机号、@ 对象在送进模型前替换为占位符
蒸馏：单块 50k token、总量上限 150k，最多 3 块，块间并发 2 路
产物：SKILL.md + 证据索引 + 生成报告，打包为 ZIP
────────────────
⚠️ 注意事项
· 产物是基于群聊样本的框架推断，不代表本人确认，也不能当成本人发言
· 会消耗「{提供商标签}」接口额度：样本少时通常 1–3 万输入 token，样本多时最多约 15 万
· 覆盖范围受两个上限约束：原文保留期（{N} 天）与最多 60000 条原文；群极活跃时只覆盖最近那段
· 全程约 1–5 分钟（块数多时更长），期间不要重复触发；同群同一时间只允许一个任务
· 只读本群、只读该成员；跨群记忆与群公共记忆不参与
· 本群未授权记忆采集时改用群历史接口扫描：更慢，且受接口限流影响
· 产物落盘在 data/chatgpt/nuwa-skills/ 下，ZIP 默认发到你的私聊
回复 Y 开始，回复其他内容取消（180 秒内有效；是 / 确认 亦可）
```

- 提供商标签取 `e.modelProviderId || Config.defaultProviderId`，经 `findProvider` / `providerLabel` 转可读名，查不到原样打印 id；保留天数取 `Config.memoryGroupCapture.rawRetentionDays ?? 30`。

**取样**

- 数据源是本群记忆采集（`memoryGroupCapture.groups` 里授权且开启的群）写进 Redis 的原文 + `user_group` 事实。授权只决定「能不能读」，不决定「读多少」。
- 本地读取改为**按时间分页、铺满保留期**：固定 `endTime` 后按 `ZREVRANGEBYSCORE … LIMIT offset, pageSize` 往回翻，每页批量取值，直到保留期起点或 60000 行为止。固定 `endTime` 是分页正确性的前提——扫描期间新到的消息时间戳更大，不会挤动区间内的偏移。
- 存储层新增分页读取方法，与既有「最近原文」方法（图谱在用）共用一个批量取值助手；后者的语义与 20000 上限都不动。
- 页内行先在内存里按发送者过滤（跳过空文本与指令消息），得到候选样本；**候选 ≤ 6000 全取，超过才等距抽 6000 条**，首尾必留。
- 总量预算由 100k 提到 150k（6000 条 × 30 字 ≈ 15 万 token，正好 3 块），单块仍是 50k。这不是「预算变便宜了」，而是「要用 6000 条就必须给 150k」——100k 只装得下约 4000 条。
- **块数硬上限 3**：总量抽样会因「首条必留」略微超出预算（最多一条消息的量），单块 50k 就可能切出第 4 块。`chunkEvidenceRecords` 因此接受 `maxChunks`，超限时把单块预算抬到 `ceil(总量/3)`——宁可单块略高于 50k，也不打破确认文案里承诺的块数。
- 为什么封顶 6000：200 条/天 × 720 天 = 14.4 万条 ≈ 360 万 token、72 块、并发 2 路也要一小时以上，跑不动也不必跑。三重验证要的是「跨话题复现」，720 天里话题早已饱和，6000 条（约 8 条/天）足以铺满常规话题。
- 本地候选不足 30 条才回退历史扫描（扫描上限 20000），语义不变。

**执行**

- 确认后先回一条「开始蒸馏，约 1–5 分钟」，再执行；中途不发分块进度。
- 编排从工具类整体迁出为一个独立的运行入口：`runGroupMemberDistill(e, { targetId, requestedCount })`，返回结构化结果（`skillMarkdown`、`artifact`、`summary`）而不是给模型看的字符串。
- 脱敏、切块、合成、自检、落盘、增量更新逻辑原样保留，只把「工具参数校验」换成「指令已校验过的入参」。
- 日志前缀由 `[GroupMemberSkillTool]` 改为 `[Nuwa]`。
- 失败回复保留产物相对目录（相对 `process.cwd()`），不打印绝对路径。

**投递**

- 产物打包后优先私聊发给触发者：`e.bot.pickFriend(e.user_id).sendFile(zipPath, zipName)`。用 `e.bot`（触发事件的那个账号）而不是全局 Bot，多账号下才落对。
- 该接口返回值不统一（有的适配器给 `{ time, status }`，有的返回 `void`），**不以返回值判成功，只看是否抛错**；抛错就回退当前群，并在摘要里注明。
- 回退顺序在选定通道内：ZIP 失败 → `SKILL.md`；两级都失败就由摘要说明「附件发送失败」并给出产物目录，不再有第三级文本投递（原工具也没有）。
- 结束时一条摘要：样本条数、置信度、心智模型/启发式/表达 DNA 数量、自检结果、耗时、产物目录、ZIP 去向。
- 去掉原工具末尾「让模型点评这份 SKILL.md」的环节——指令没有主模型在场，摘要由确定性数据拼出。

**并发**

- 模块级 `Set` 按群号去重，登记在确认之后、执行之前，`finally` 释放；不跨进程、重启重置，与 `#at图谱` 同款。
- 重复触发回「本群已有蒸馏任务在跑，请等它结束」。

**删除工具形态**

- 删除工具类文件与 `model/core.js` 里的 import 与可选工具注册项；模型侧不再看到这条能力。
- 纯逻辑模块保持无 Config / Redis / 子模型依赖，新增的三个函数都是纯函数。

## Testing Decisions

好测试只断言对外可观察的结果：解析出哪个目标、返回哪种拒绝原因、抽样后条数与首尾是否保留、确认词认不认。不断言内部调用次数，不测 I/O 编排。

- **测的模块**：`utils/groupMemberSkill.js`（纯逻辑）。
- **新增用例**：
  - `parseDistillTarget`：@ 一人 / 引用消息 / 纯数字 / 无目标 / @ 多人 / @ 全体 / @ 与数字冲突 / @ Bot 自己，各自返回目标或拒绝原因。
  - `isConfirmWord`：`Y`、`y`、`yes`、`是`、`确认`、`确定` 通过；`好`、`n`、空串、`开始` 不通过。
  - `sampleRecordsByCount`：不足 N 条原样返回；超过 N 条时恰好 N 条、首尾必留、位置等距。
- **先例**：本仓 `test/groupMemberSkill.test.mjs` 既有的纯函数用例（切块、抽样、质量自检），以及 `#at图谱` 的入参解析口径。
- **不测**：真模型、真 Redis、真 OneBot 发送；`awaitContext` 时序由宿主提供。

## Out of Scope

- **继续抬高整体量级（500k / 10 块）**：上游 6 个 agent 累计 500k token 是高密度语料，群聊信噪比低得多；堆到 10 块只让合成输入变长、耗时翻倍。150k / 3 块是当前上限。
- **突破原文保留期**：TTL 到期后原文已删除，任何读取方式都补不回来。
- **条数参数与按天分层抽样**：等距抽样已能铺满窗口；更细的分层留待有实际需要时再谈。
- 工具与指令双入口共存。
- 分块进度消息、群内投票确认、多目标批量蒸馏。
- 真实链路验收（需部署后看日志与产物）。

## Further Notes

- **上游核实**（`alchaincyf/nuwa-skill` 的 README 与 `SKILL.md`，2026-10-30）：README 不含 token 数字；`500k` 出现在 SKILL.md 的「常见失败模式」表——「单次完整蒸馏可累积 500k+ token，200k 窗口模型跑不完」，指的是 6 路调研 agent 的**累计**输入，不是单次调用，也不是单块预算。上游对策是「分 Phase 续跑 + 调研文件即断点」，与本仓「分块 + 每块落盘」解的是同一个问题。故 `chunkTokens: 50000` 与上游单 agent 量级（500k/6 ≈ 83k）同阶，`maxInputTokens` 是本仓自定的采样上限，无上游契约可对齐。
- **条数算术**：按本仓 `estimateTokens`（中文 1.2 字/token），500 条 × 30 字 ≈ 1.25 万 token，2000 条 ≈ 5 万，6000 条 ≈ 15 万，14.4 万条 ≈ 360 万。
- **未解决的口径问题**：720 天的均匀抽样会把「两年前的他」和「现在的他」平均成一个人。上游用「人生时间线」agent + 双 agent 评估处理立场迁移；本仓产物明确不写时间线，态度变化可能被记成 `tensions`（保留矛盾是刻意的），也可能被抹平。想让产物更贴「现在的他」，调小保留期比调条数更有效。
- **术语**：`女娲蒸馏`（指令）与 `分块预算` 已收录进 `GLOSSARY.md`；「群友 Skill」仍是产物名，不是入口名。
