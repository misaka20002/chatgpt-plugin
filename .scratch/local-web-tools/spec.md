# spec：纯本地搜索与网页读取工具（无反爬）

Status: ready-for-agent

- 决策来源：2026-10-21 三轮问答（定位 / 反爬边界 / 去 Python / 并发取正文 / 通道选择 / 引擎集合 / 转换器实现 / 契约复用）
- 术语：「网页读取」「续读」见根目录 `GLOSSARY.md`（本 spec 会把「网页读取」拆成「托管提取」与「本地抓取」两条）
- 前置决策：`docs/adr/0004-hosted-web-extraction-over-self-hosted-fetch.md`（托管提取优先）；本次新增 ADR 0005 记录本地通道的实测依据

## Problem Statement

插件里有两个「不用任何 Key」的联网工具，现在都不能用或者很难用。

**搜索工具**（锅巴「呆毛纯本地搜索工具」）用 `execSync` 调 `utils/web_search.py`，要求用户自己装 Python 3 + `aiohttp` + `beautifulsoup4`。实测这台机器上 Python 在、依赖没装，工具直接返回「Python依赖缺失」。即便装好，它也是：搜到 N 条后**串行**抓每条结果页、每条只留 700 字符、单页 6 秒超时——5 条结果最坏要 30 秒以上；搜索请求本身默认先试 Bing 再 Google 再搜狗，而 Google 这条早就死了（见下）；输出是「1. 标题 / 摘要 / === 搜索总结 ===」的老格式，没有不可信声明、没有总长上限，网页里的「忽略前面的指令」会原样进上下文。

**网页读取工具**（锅巴「呆毛纯本地网页读取工具」）走 puppeteer：每次调用 `new ChatGPTPuppeteer()` 连 `127.0.0.1:51777`（没有就现起 Chromium），`finally` 里 `browser.close()`——如果连的是共享实例，**这一下会把插件自己的头像/数学渲染一并关掉**。它还临时改全局 `Config.headless` 再改回来，异常路径上改不回来；`page.goto` 用 `networkidle2` 且没有超时；拿到 HTML 后用一串正则清洗，没有长度上限、没有续读、没有不可信声明，`<head>` 被整段删掉连 `<title>` 也没了。

**Google 已不可用**（实测）：`googlesearch-python` 1.3.0 在 en / advanced / zh-CN+cn 三种参数下都返回 0 条；`fetch https://www.google.com/search?q=…` 拿到 200 但正文是「如果您在几秒钟内没有被重定向，请点击此处」的 JS 跳转页；`gbv=1`、`udm=14` 两个老的非 JS 入口同样 0 个结果节点；puppeteer 打开搜索结果也是 0 条。这条路已经彻底死掉，留着只会拖慢降级链。

## Solution

两个工具都改成**纯 Node、纯 HTTP、零额外运行环境**：不装 Python、不装 Chromium、不要任何 Key，作为「托管提取都不可用时的最后兜底」存在，不承诺质量，失败要说清原因。

- **搜索**：Bing → DuckDuckGo(HTML) → 百度，任一成功即返回；三个引擎都有结果解析器。结果里的正文抓取改为**并发**取前 3 条、每条 2000 字符、整体 8 秒硬超时，抓不到就只给摘要。
- **读取**：照 opencode `webfetch` 的形状——一次 GET、按 `content-type` 与 `meta charset` 解码、HTML 转 Markdown、30 秒超时、5 MiB 字节上限。输出复用现有契约（`Provider / URL / Title` 头 + 不可信声明 + 20000 字符 + `start` 续读）。

两个工具的定位、失败语义与输出形状都与 `exa_webfetch` / `parallel_webfetch` / `tavily_*` 对齐，模型不需要为「本地」记第二套格式。

## User Stories

1. 作为没有填任何搜索 Key 的部署者，我希望「纯本地搜索」开箱就能用，这样我不用先 `pip install` 三个 Python 包。
2. 作为没有装 Chromium 的部署者，我希望「纯本地网页读取」也能读网页，这样我不必为了读一个链接去装浏览器。
3. 作为群里的提问者，我希望搜一个词能在两秒内拿到结果，而不是等五个页面串行超时。
4. 作为群里的提问者，我希望搜索结果带一点正文摘录，这样我能判断哪条值得点开。
5. 作为群里的提问者，我希望搜索结果里的链接是**真实地址**，而不是 `baidu.com/link?url=…` 这种点开才知道去哪的跳转链。
6. 作为群里的提问者，我希望三个引擎里的某一个被限流时，工具自己换下一个，而不是整次搜索失败。
7. 作为群里的提问者，我希望三个引擎都失败时看到的是「Bing: HTTP 403；DuckDuckGo: 请求超时；百度: 解析不到结果」这种可归因的失败，而不是一句「没有结果」。
8. 作为群里的提问者，我希望读长文时先拿到前 20000 字符，并被告知怎么续读，而不是被硬截断后再也读不到后面。
9. 作为群里的提问者，我希望 GBK / gb18030 的老站点不乱码。
10. 作为群里的提问者，我希望 PDF、图片这类非文本内容被明确告知「不支持」，而不是把二进制垃圾塞进上下文。
11. 作为群里的提问者，我希望站点返回 403 时工具说「HTTP 403」，而不是假装读到了空页面。
12. 作为 Bot 主人，我希望网页内容始终带「不可信数据」声明，这样提示注入不会因为换了工具就失去标记。
13. 作为 Bot 主人，我希望读网页不会把插件自己的头像/数学渲染用的 Chromium 关掉。
14. 作为 Bot 主人，我希望一次网页读取失败不会把全局 `headless` 配置留在错误状态。
15. 作为 Bot 主人，我希望模型不能通过网页读取工具访问 `127.0.0.1` 或内网地址，避免把本机管理面板、NAS、路由器的内容读出来发到群里。
16. 作为维护者，我希望搜索工具的实现只有一份、可测试，而不是「JS 编排 + 一段没人测的 Python」。
17. 作为维护者，我希望新增测试不触网，靠 fixtures 就能覆盖三个引擎的解析与降级顺序。
18. 作为维护者，我希望锅巴里的帮助文案不再要求用户安装 Python。
19. 作为维护者，我希望 `GLOSSARY.md` 能区分「托管提取」和「本地抓取」，不再用一条「网页读取」定义两种实现。
20. 作为未来的读者，我希望有一份 ADR 说明「0004 说不要自建抓取，为什么现在又做了本地抓取」，并且能看到当时的实测数据。
21. 作为模型，我希望工具描述明确告诉我「这是本地兜底，不支持 JS 渲染与登录墙」，这样我在读失败时不会反复重试同一个 URL。
22. 作为模型，我希望「本地读取」与「Exa/Parallel 读取」的输出形状一致，这样我不用为不同工具准备不同的解析方式。

## Implementation Decisions

**总体**

- 两个工具都改为纯 Node 实现，零新增运行环境（不依赖 Python、不依赖 Chromium）。
- 工具名不变：读取工具仍是 `website`（锅巴键 `local_WebsiteTool`），搜索工具仍是 `web_search`（锅巴键 `misaka_WebSearchTool`）。改名会牵动既有的重名处理与历史提示词，收益不足。
- 两者仍由锅巴「搜索/网络来源」（`serpSourceArr`）控制启用，沿用现有注册映射，不新增注册机制与配置字段。
- 删除 `utils/web_search.py`；锅巴里 `serpSourceArr` 的帮助文案删掉 python3 / pip 那段。

**本地取页模块（新增，两个工具共用）**

- 一个函数负责「给 URL，拿回解码后的 HTML 或文本」，职责固定为：协议校验 → 私网校验 → 发请求 → 跟随重定向 → 字节上限 → 编码判定 → 解码。
- 只接受 http/https；带内嵌用户名密码的 URL 直接拒（复用既有的 `requireHttpUrl`）。
- **拒绝私网目标**：目标主机解析出的任一地址落在 loopback / 私有 / 链路本地 / `0.0.0.0` 段时直接失败；每一跳重定向都重新校验。错误文案要让模型知道「这是被策略拦下的」，而不是「站点挂了」。这是本地抓取特有的 SSRF 面，托管提取没有这个问题。
- 重定向自己跟（最多 5 跳），不把跟随交给运行时的 `redirect: 'follow'`——否则每跳都无法重新校验主机。
- 编码判定顺序：`content-type` 的 `charset` → 前 4 KiB 里的 `<meta charset>` → utf-8。`gbk` / `gb18030` / `big5` 由 Node 的 `TextDecoder` 直接支持，不做额外转码。
- 非文本 `content-type`（`application/pdf`、`image/*`、`application/octet-stream` 等）在读取正文前就失败，提示「不支持的内容类型」；不尝试解析。
- 响应体上限 5 MiB、超时 30 秒；超限与超时都归一成带原因的失败。
- 复用既有的传输模块承载字节上限、超时归一与取消未消费响应体，不另写一套 `fetch` 封装。

**HTML→Markdown（新增）**

- 移植 opencode 的 `html-markdown.ts`（含 `extractTextFromHTML`），转成 JS 并保留其行为；新增运行时依赖 `htmlparser2`。
- 不自己写精简版：这次选型就是用该转换器跑完 22 个目标才定的，重写等于把它的边角再踩一遍。
- 标题从**转换前**的原始 HTML 取（`<title>`），因为转换器会丢掉 `<head>`。

**搜索工具**

- 引擎顺序硬编码：Bing → DuckDuckGo(HTML) → 百度；前一个抛错或解析为空就换下一个，全失败才返回 `Error:` 并附每个引擎的原因。
- 各引擎的解析依据：Bing 的结果节点是 `li.b_algo`，标题链接在 `h2 > a[href]`，摘要在其后第一个 `<p>`；DuckDuckGo 走 `html.duckduckgo.com/html/`，结果链接类是 `result__a`、摘要是 `result__snippet`，真实地址藏在 `uddg` 查询参数里，取出后要 URL 解码；百度的结果块是 `div.result`，标题链接在 `h3 > a`，跳转链的真实地址在结果节点的 `mu` 属性里。
- 引擎失败不重试、不退避：一次失败就换下一个，避免一次工具调用被重试拖长。同一引擎连续失败不做全局熔断（单进程内的记忆会引入状态与过期策略，收益不足）。
- 正文抓取：并发取前 3 条，每条截 2000 字符；整体 8 秒硬超时（同一个 signal 传给所有请求），失败的那条退回只给摘要。并发失败不视为整体失败。
- 输出形状与 `tavily_search` 同构：`Web search results from 本地搜索 (<命中的引擎>) for "<query>" (<不可信声明>):`，每条是 `## [标题](url)` + 摘要 + 正文摘录；总长用同一套封顶。
- 参数保持 `query` + `max_results`（1–20，默认 5）；不新增 `site:`、时间范围等 passthrough 参数。

**读取工具**

- 参数只有 `url` 与 `start`；不提供 `format`、不提供 `timeout`（固定 30 秒，与 opencode 默认一致）。
- 正文 = 转换器输出的 Markdown；`title` 取原始 HTML 的 `<title>`，取不到时用 `(untitled)`。
- 输出复用既有契约模块（`Web page content from 本地抓取 for <url> …` + `Title:` + 正文 + 截断标记 + `start` 续读）。续读＝重新下载整页再切片，与 Exa 每次重取一致；上限与越界语义与既有工具完全相同。
- 正文转换后为空时按失败返回，不再返回「the content of the website is:」加空串。
- 删除 puppeteer 通道与 `cleanHTML` 正则清洗：这同时消除了「关掉共享 Chromium」与「改全局 `headless`」两个 bug，不需要单独修。
- 工具描述改成：本地读取、不支持 JS 渲染与登录墙、失败会给原因、需要更高质量时改用 Exa/Parallel。

**文档与决策记录**

- `GLOSSARY.md` 把「网页读取」拆为**托管提取**（抓取与正文提取都在供应商侧）与**本地抓取**（插件自己发 HTTP、自己转 Markdown）两条；`续读` 保留，补一句本地抓取也重新下载。
- `docs/agent-guides/tools.md` 的「网页读取」小节补本地工具：它是兜底、无 JS 渲染、有限流与反爬时的表现；删掉「需要 JS 渲染的页面仍用 `local_WebsiteTool`」。
- 新增 ADR 0005：记录 22 个目标的实测对比、为什么 0004 的「不做本地抓取」结论不覆盖这个既有工具、以及为什么在「HTTP / 自动回退 / 保留 puppeteer」里选了纯 HTTP。
- ADR 0004 不改（它约束的是两个新工具的选型），由 0005 显式引用。

## Testing Decisions

**好测试的标准**：只断言外部可见行为——给什么输入、桩返回什么响应，`func` 返回什么文本、发了哪些请求、有没有发请求；不断言内部函数名、私有字段或实现顺序。测试不触网、不需要 Key、不依赖 Python 或 Chromium。

**接缝**：主接缝沿用上一批工具的既有做法——**工具实例的 `func(opts, e)` + 替换全局 `fetch`**。不为测试拆生产模块、不导出内部实现。三个引擎的解析器是纯函数（HTML 字符串进、结果数组出），可以单独做表驱动断言，这不是新接缝，只是对已有函数的直接调用。

**覆盖：只保底，不求全**（明确取舍：漏掉的场景等真出问题再补，不为假设写测试）

一个测试文件，五条：

1. 读取正常 HTML：拿到契约头、Markdown 正文、按标记续读能取到后续片段（一条用例覆盖契约与切片）。
2. 私网地址（`127.0.0.1`、`192.168.x`）被拒，且没有发出任何请求。
3. 搜索结果解析：百度取 `mu` 得到真实地址、DuckDuckGo 解码 `uddg`（同一条用例里断言两条结果，不按引擎拆文件）。
4. 引擎降级：Bing 抛错时换 DuckDuckGo 并成功返回。
5. 非文本 `content-type` 被拒（PDF 一类不塞进上下文）。

刻意不测：编码矩阵（GBK 只在实现里按三级回退处理）、重定向跳数、字节上限、超时、403、`max_results` 边界、并发部分失败的组合。这些是「已经知道怎么写」的分支，等真出 bug 再补。

- 先例：`test/exaWebFetchTool.test.js`、`test/opencodeWebSearchTool.test.js`（工具实例 + 全局 fetch 桩）。

**接线**：新增测试文件接进 `test:tools`；`test:tools` 不进 `check`（沿用「check 只留核心门禁」的既定取舍）。

## Out of Scope

- 反爬：cookie 池、代理轮换、UA/指纹伪装、验证码、TLS 指纹（`cycletls`）。工具名里的「无反爬」是承诺，不是未完成项。
- JS 渲染：不保留 puppeteer 通道，也不做「HTTP 失败自动回退渲染」。纯客户端渲染的站点读不到就是读不到。
- 登录态：不读需要登录的页面，不持久化 cookie。
- PDF / 图片 / Office 文档解析。
- Google：已实测死路，不实现也不留降级位。
- 搜索高级语法（`site:`、时间范围、站内搜索）与结果去重/重排。
- 不改 `exa_webfetch`、`parallel_webfetch`、`tavily_search`、`tavily_website_extract`。

## Further Notes

**实测对比（2026-10-21，单机单 IP，Edge headless，同一转换器）**

正文页两条路等价（纯文本字符数，HTTP / Puppeteer）：

| 目标 | HTTP | Puppeteer | HTTP 耗时 | Pup 耗时 |
| --- | --- | --- | --- | --- |
| MDN 文档 | 17031 | 17021 | 1028ms | 2497ms |
| 维基百科 | 31964 | 32233 | 1380ms | 3091ms |
| Node 文档 | 115983 | 115946 | 528ms | 4195ms |
| HN 首页 | 4064 | 4064 | 1436ms | 1728ms |
| solidot | 11585 | 11548 | 549ms | 1395ms |
| 豆瓣首页 | 4037 | 4294 | 296ms | 1312ms |
| CSDN 文章 | 11473 | 10189 | 695ms | 2909ms |
| 简书文章 | 2815 | 3262 | 1294ms | 3422ms |
| react.dev | 9000 | 9045 | 602ms | 2383ms |

puppeteer 明显更多、但多的是壳不是正文：GitHub 仓库 6228 → 13853（文件列表）、B 站视频 1438 → 4165（评论）、掘金首页 341 → 3617（分类导航）、淘宝首页 503 → 8879（全站导航）。

两边都进不去：知乎问题/专栏 403（puppeteer 也是 403，返回「请求存在异常」）、Reddit 403。PDF：HTTP 拿到二进制、puppeteer 30 秒导航超时。

**时间成本**：HTTP 单页 0.14–2.1 秒（中位约 0.6 秒）；puppeteer 1.3–5.3 秒（中位约 2.9 秒），另外常驻一个浏览器进程，冷启动 217ms。

**样本局限**：22 个目标、单机单 IP、以中英文主流站为主。纯客户端渲染且无 SSR 的内容站理论上会让 HTTP 拿不到正文，但这批样本里没有出现——出现的「只有 JS 能读」全是登录墙。

**引擎实测**：Bing 200 / 10 条 / 331ms；DuckDuckGo HTML 200 / 10 条 / 1.16s（`uddg` 解出真实地址）；百度 200 / 9 条 / 1.01s；搜狗 200 / 可解析但链接是 `/link?url=` 跳转，且与百度中文结果高度重叠，故不采用。Google 三条路（直连、`googlesearch-python`、puppeteer）全部为 0 条。

**私网拦截已确认**：这条在访谈之外，写 spec 时补的。理由是本地抓取是典型的 SSRF 面（模型可以把 `http://127.0.0.1:6099` 这类地址塞进参数，结果还会发到群里）。已与需求方确认保留，代价是「读自家路由器/NAS」这种用法不再支持。
