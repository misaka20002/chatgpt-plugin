# 引用图在工具轮里活下来

Status: ready-for-human

## Problem Statement

用户引用一张图问「这是什么」，模型决定调一个工具（搜一下、查一下天气、读一条群公告都算）。工具返回之后，模型像从没看过那张图：要么答非所问，要么说「我看不到图片」。用户看到的是「明明刚发过图，问一句话就失忆了」。

`mediaRecognitionSource = 原生多模态` 时，引用图会以 base64 直接内联给四个 provider。但只有 Gemini 与 OpenAI Chat Completions 会丢图：

- **Gemini**：工具轮是一次新的 `sendMessage` 递归，历史从存储重新读；存储时 `inline_data` 已被换成 `[多媒体附件: mime]` 占位符，第二次请求里只剩这行文本。
- **OpenAI Chat Completions**：第一次响应结束时 `_stripImages()` 把 `image_url` 换成 `[图片]` 再落库；工具轮沿父链重走历史，读到的就是 `[图片]`。

Claude（工具循环在单次调用内、历史常驻内存）与 OpenAI Responses（无状态分支把本轮 input 常驻内存整体重发；`store=true` 时上下文在服务端）不受影响。

## Solution

工具轮继续使用**最初那一轮用户消息的原始内容**（文本 + 图片），但存储形态不变——库里仍然只有占位符。原始图片只在这一次请求的生命周期内存在，由调用方显式传给客户端，客户端在拼请求体时按消息 id 回填到那一轮。

对外表现：引用图问一句需要调工具的话，工具返回后模型仍然看得见图。

## User Stories

1. 作为群聊用户，我引一张图问「这图里的人是哪个动漫角色」，机器人调完搜索工具后能接着按图回答，而不是说「我看不到图片」。
2. 作为群聊用户，我希望引图和普通提问的行为一致——调不调工具都不影响模型对图片的理解。
3. 作为群聊用户，我不需要为了让模型「记住图」而重复发一遍图。
4. 作为使用 Gemini 的用户，我希望工具返回后模型能对比「图里的内容」和「工具查到的内容」，而不是只能凭工具返回的文字猜。
5. 作为使用 OpenAI Chat Completions 的用户，我期望与 Gemini 相同的体验，不因为换 provider 就换一套毛病。
6. 作为使用 Claude 或 Responses 的用户，我的现有体验不应被这次修复改变。
7. 作为部署者，我不希望修复让 Redis 里开始堆积 base64——历史消息的体积必须和现在一样。
8. 作为部署者，我不希望修复引入新的失败模式：回填找不到目标消息时要静默降级成现有行为，不能让整轮对话报错。
9. 作为维护者，我希望第二次请求的形状与第一次一致（同一段 `contents` 前缀），这样它天然落在官方已验证的请求形态里，而不是一次没验证过的协议尝试。
10. 作为维护者，我希望有一条测试能钉住「图片恰好出现一次、在用户轮、不在 functionResponse 轮」，防止以后又被「别重复带图」的直觉改回去。
11. 作为维护者，我希望「库里从不存 base64」也有测试守着，避免修复顺手把图片塞回存储。
12. 作为后来接手的人，我希望术语表里能分清「本轮原始内容」与「媒体占位」——这次 bug 正源于两个概念在各处叫法不同。

## Implementation Decisions

- **不改存储形态**：引用图落库继续只写占位符（Gemini `[多媒体附件: mime]`、OpenAI `[图片]`）。跨轮可见性（下一轮对话仍能看见历史图）不在本次范围，它是另一个取舍（存储成本 vs 跨轮可见性），AstrBot 在这点上选的是相反方向。
- **新增一个逐轮透传字段**，语义是「本轮用户消息的原始内容 + 它属于哪条消息」，只活在本次请求的内存里，不落库。字段名随协议、形状也随协议：Gemini `turnParts`（`{ id, parts }`，**客户端在第一轮自建**，递归时透传），OpenAI Chat `turnContent`（`{ id, content }`，**由 `core` 在发起工具轮时提供**）。不用同一个名字承载两种形状，也不跨 provider 复用——主备切换会重建 option。
- **Gemini 客户端**：不再从历史里「恢复」图片，而是在**拼请求体时**按 `turnParts.id` 把那条消息的 parts 换成「本轮原始内容」；首段文本仍以历史为准（`syncInnerOs` 可能刚写入全局提示），其余 parts 用原始内容。`functionResponse` 轮仍然不挂图——这条既有约束保留，并与本次修复不冲突（图留在最初那一轮）。**历史对象一律不原地改**：工具轮的历史来自 `createAttemptHistory` 的内存 Map，取到的是共享引用，原地赋值会把 base64 写回存储（实现时被测试当场抓到）。
- **OpenAI Chat Completions 客户端**：`_buildMessages` 遍历父链读到与 `turnContent.id` 相同的消息时，用 `turnContent.content` 作为该消息的请求内容（构造副本，不原地改存储对象）。
- **OpenAI Chat 分支的调用方**：进入工具循环**之前**记下本轮用户消息的 id（第二轮起响应消息的 parent 已经是 tool 消息，不能再取），工具轮把它与第一轮的原始多模态 content 一起放进 `turnContent`；无图时不设置该字段，普通路径不受影响。
- **不采用的两条路线**：把 Gemini 的递归改成 Claude 式的内存循环（要同时动存储剥离、全局提示注入、历史归一化与 thoughtSignature 四条链）；把 base64 留在 Redis（体积不可接受）。理由与一手证据见同目录 `research.md`。
- **文档不变式**：provider 指南的「引用图原生多模态」小节补一条——原始媒体只活在请求里，工具轮靠回填而不是靠落库；术语表补「本轮原始内容」「媒体占位」两个词；新增一条 ADR 记录取舍。

## Testing Decisions

- **测什么**：客户端对外发出的**请求体**。好测试只断言「第二次请求里图片字节恰好出现一次、位于用户轮、functionResponse 轮不含」，以及「会话链上的用户/工具消息没有图片字节」；不断言内部函数调用次数或字段名之外的实现细节。响应消息里的 `conversation` 请求副本不在断言范围（既有行为，见 Further Notes）。
- **最高现有接缝**：`test/providerClients.test.mjs` 已经用假 fetch 截获四个协议客户端真实请求体，是这件事最高、也是唯一的接缝，不新增接缝。
- **要改的现有用例**：`Gemini 工具轮回填不再重复携带引用图（invalid argument 回归）` 现在断言「第二次请求完全不含图片字节」——它把 bug 钉成了期望。改为断言「恰好一次、在用户轮、回调轮没有」。
- **要新增的用例**：OpenAI Chat Completions 的同形用例（首轮带图 → 工具轮 → 校验第二次请求体的消息序列），并断言存储里仍是 `[图片]` 占位符。
- **core 层覆盖**：`model/core.js` 里「记下用户轮 id → 工具轮传 `turnContent`」只有调用方自己执行，客户端测试手抄调用方逻辑不算覆盖。在 `test/providerContext.test.mjs`（已用真实 Core + 假网络跑四个协议）补一条：只桩掉引用图下载（`loadQuotedImages`，外部边界），断言 `api` 与 `gemini` 第二次请求里图片恰好一次、位置在用户轮。stub 要保留「没有 `e.img` 就没有图」的真实语义，否则会改变同文件其它用例的请求形状。
- **先验**：同文件的 `Gemini 工具回填保持完整历史链` 已经用 `createAttemptHistory` + 假 fetch 校验请求体结构，新用例沿用同一套装置。

## Out of Scope

- 跨轮图片可见性（下一轮对话、进程重启后仍能引用历史图）：需要重新设计存储形态，与「Redis 不存 base64」冲突，单独立项。
- 引用图之外的其他媒体（视频、`SubLLM` 的单图识别）：`SubLLM` 从不发送 tools，主对话也不内联视频，本次不涉及。
- 工具**返回**的图片如何进入上下文（AstrBot 的 tool image cache 那套）：本仓没有这条路径。
- 计划中顺带发现的注释措辞（「AstrBot 同样只在用户消息里放图片」）只改到与事实一致，不重写整段文档。

## Further Notes

- 一手依据：Google 官方 `contents` 无状态语义与多模态 function calling 示例、AstrBot 4.29.3 的实现（它不剥离 base64，历史自足）。见 `research.md`。
- 成本：修复后每轮工具调用都会重发图片，token 成本随轮数线性增长——Claude 与 Responses 现在就是这样，这是 stateless 协议的固有代价，不是回归。
- 已知限制：回填依赖「当次请求内还记得原始 parts」。历史被 `chatgptBlockCount` 截断到只剩工具链时，目标轮可能已不在请求里，此时静默降级为现状（占位符），不报错。
- `turnParts` 在有图的非工具轮也会被记录（发生在第一轮的消息构造处），但只有工具轮才会消费它；没有工具时不记录，避免 SubLLM 单图识别白拷一份 base64。
- OpenAI 的响应消息带一份 `conversation` 请求副本（`apps/chat.js` 的建议回复会读它），里面仍有 base64——既有行为，本次不清理；因此不要把「库里没有 base64」写成全称结论。
- 回放 content 时必须逐段复制：`syncInnerOs` 会原地改首个 text part，共享数组会把全局提示写回调用方持有的原始内容（评审发现，已加回归断言）。
