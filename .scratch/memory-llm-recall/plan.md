# 记忆 V2：95% 单作用域独立压缩方案（最新版）

状态：**实现已写入当前工作区，待真实环境验收与提交**。本文件记录已实施的 95% 夜间独立压缩方案，取代此前 80% 系统提示词方案。
日期：2026-10-22。

## 2026-10-23 最新修订（覆盖下方冲突描述）

- 锅巴个人最小容量改为 **50**、群公共最小容量改为 **20**；默认仍是个人100、群公共50。
- >95% 仍只启动**一次夜间压缩任务**，但该任务若整体超 Token 预算，先随机打散有效记忆，再按 Token 限制拆成两个或多个片段；**每片各发一次 LLM POST**，分片模型只审阅、操作自己片内 ID，服务端逐片复核快照。输出目标按片段记忆数比例分摊，尽量使全局剩余 <=70%。
- 分片处理完仍未达到目标时只 `logger.warn`，不得追加第二轮补救 POST；底层网络重试遵循用户既有许可。单条记忆超过预算时保留并记录告警，其余片段继续执行。
- 本节替换下方“单个 scope 只发一次 POST”“超预算整个跳过”“Guoba min100/min50”等旧措辞。

## 需求不变式

1. **常规凌晨 04:00 提炼不按成员追加模型请求**：原有 `DailyConsolidation` 继续遍历已授权群、日窗口及 Token 分片；每个模型分片本来可以同时抽取多个发言人的原子事实。
2. **全时写入去重**：现有 `applyCandidates/applyFact` 同作用域同键值的精确去重不变；跨键语义重复可将少量相关旧记忆传入原来已有的提炼模型请求辅助去重，无论是否接近容量均执行，**不得因此另发按成员划分的模型 POST**。
3. **仅超过 95% 时额外压缩**：每日提炼结束后扫描 Redis 的三个逻辑作用域：跨群个人 `user(uid)`、每群个人 `user_group(uid,gid)`、群公共 `group(gid)`。各按所属独立配置 `cap` 计算，`count > cap*0.95` 才让该作用域创建**一次压缩任务**（任务内按 Token 预算分片、每片一次 POST）；当日没群聊的超阈值作用域也应参与（延续 Q11 A）。达到 95% 但未超过时不调用。比较 `validTo` 排除过期及 archived。
4. **压缩到不超过 70%**：LLM 审阅被触发作用域的完整、带 ID 的有效历史记忆，综合独特性、证据、可靠性、时效、未来用途、信息覆盖面决定 `keep/merge/archive`，目标剩余 `<= floor(cap*0.7)`。不能仅按 importance/createdAt 删除。服务端校验 ID 属于该作用域、状态和版本、来源、证据集合，优先归档而非直接物理删除。若不能安全达到目标，允许本次未达标并记录，**绝不回退分数淘汰**。
5. **实时允许暂时超额**：`Memory_Tool` 有效写入依旧通过所有事实归属、权限、证据和同值去重校验，达到配置 cap 后不拒绝、不触发 `_evictLowest`；不加实时维护系统词或同步清理 POST。
6. **配置**：`maxMemoriesPerUser` 默认100，Guoba min50，作用于两类个人作用域；`maxMemoriesPerGroup` 新增默认50，Guoba min20，作用于每群公共 `group`；Guoba 新字段位于个人字段紧下方。保留已保存旧个人数值、不擅自迁移；**全量召回模式已于 2026-10-23 删除**，召回条数只由 `memoryContextLimit` 决定。
7. **成本**：额外压缩任务只按严格超 95% 的作用域创建，HTTP 请求数取决于任务内随机分片数量，不按发言成员计算；Redis `compressionAttempt` 采用 **按北京时间日期、作用域的 SET NX + 48 小时 TTL**，同一天同一作用域即使未达 70% 或模型失败也不会补发第二次 POST。`logger.warn` 记录未达目标或错误，下一天才有机会重试；实时调用不变。
8. **过期**：沿用 `MemoryStore.deleteExpired(30)` 和有效期排除规则，不依赖 LLM 或额外 POST。
9. **安全**：不跨人、跨群、跨作用域合并；历史文本是数据，不能成为指令或伪造消息证据；模型只给出候选维护动作，存储按可信 ID+快照校验执行。合并复制证据并保留来源、归档原因和时间；无法证明无损的合并应拒绝或仅进行独立的 LLM 价值归档（原因真实标注）。不新增主人的手动新增/修改/锁定入口。

## 计算例子

| 作用域 | cap | 95% | 首个触发 count | 70% 目标 |
| --- | ---: | ---: | ---: | ---: |
| `user` / `user_group` | 100 | 95 | **96** | **70** |
| `group` | 50 | 47.5 | **48** | **35** |

## 实施步骤（代码已落地，保留为设计追溯）

1. **配置与 Guoba**：`utils/config.js` 确认现有默认100，新增独立 `maxMemoriesPerGroup:50`；`guoba.support.js` 将个人 min 从 10 提到100，紧随其后新增群公共 min50；更新帮助文案，确保读取/保存无额外映射遗漏；补配置测试。此配置阶段不宣称压缩生产逻辑已上线。
2. **取消隐式评分硬淘汰**：`utils/memory/store.js` 的 `applyFact` 实时与日窗口写入取消 `_evictLowest`；保留有效事实去重、更新/撤回及来源关联。旧的 `utils/userMemory.js` 为遗留 Hash 路径，不误改其旧行为；验证 V2 不会走它。
3. **夜间检测器**：在 `utils/memory/dailyTask.js` 原提炼完成后（包含无聊天但独立整理需求），`MemoryStore` 只读枚举三类索引及有效条数；各作用域根据个人/群 cap 计算严格 `>95%`，同一 `user(uid)` 即使有多个群也只处理一次。触发后给独立 `compression` 模型请求，Provider 复用 `memoryGroupCapture.provider`。没有触发绝不 POST。
4. **专用压缩协议**：独立于旧的 group-window `candidates` 提炼 JSON，调用 `SubLLM` 返回带 ID 的 `keepIds/mergePlans/archiveIds` 和真实理由、建议目标计数。校验 JSON 和所有引用 ID 在输入可信白名单内。提示词写明：以 70% 为目标，先找等价合并，再由 LLM 综合价值决定归档；不得笼统合并不同事实，不能伪造失效。每个 scope 每晚一次压缩任务；分片时每片一次维护 POST，不复用群提炼回复格式。
5. **执行器与失败策略**：服务端快照校验 active/validTo/ID/owner/group/scope/manual、证据关系；按可靠的事务/锁安全完成证据合并、归档、审计。即使夜间新写入也不能凭旧快照清除未审阅的事实。模型失败/协议不合法/计划无法执行时不回退旧的 importance 淘汰，实际未压到 70% 必须记录原因。下一夜再按阈值尝试。
6. **常规写入前语义去重**：需在原有分片提炼提示词里带同主体且同作用域的部分或全部相关旧事实 ID，受 Token 总预算约束，不额外按成员发请求；保留现有群聊消息证据验证，不能凭旧库虚构新聊天事实。如果 Token 容量不足，仍保留存储层现有精确去重，勿无界扩张 context 或追加 Post。
7. **文档/日志/回归**：同步状态显示中个人/群 cap 与整理阈值，文档标注 Guoba 最小值和旧保存值加载语义；测试几种作用域阈值、无发言超额、扫码索引、重复 cron、失败/并发/多群个人只整理一次、专用模型输出/归档证据和旧逻辑稳定。

## 实际落地说明与限制

- `utils/memory/compression.js` 为**按 Token 预算分片的压缩任务**（一个作用域一个任务、每片一次 POST），`dailyTask.js` 的原群聊提炼完成后遍历 `store.listCompressionScopes()`；没有原文但超阈值的作用域同样处理。
- `store.applyCompressionPlan` 校验旧记忆完整快照、主体/群/作用域、全体 ID 覆盖及 `manual` 保护；同键同值或同种类且事实文本完全相同才允许无损证据合并；其它疑似语义相近事实由 LLM 提出**容量取舍归档**建议，不强行合并不同原子事实。
- 归档使用 Redis Lua CAS 防止覆写已更新的事实，归档记录 `originalSource`、`archivedAt` 与真实理由；归档项不立即物理删除，保留证据并按 30 天历史宽限清理。多个操作是逐项条件提交而非跨多键 Redis 原子事务，部分失败时返回 `partial` 并告警、不补发 POST；真实高并发/崩溃的完整恢复仍须线上验证。
- 常规提炼同一分片里最多附带 8000 字符历史记忆作去重参考（分片预算为常量 50000、不可配置，历史约占 13%、不额外扣减），不额外发按人 POST；若历史太多无法完整纳入，只能保障存储精确去重和已有上下文内的尽力语义去重，不宣称 100% 跨键语义去重。
- 单作用域压缩不再因整体过大而跳过：超出预算时随机分片逐片 POST，只有**单条**记忆本身超预算才保留该条并 `logger.warn`。失败时保留旧事实并记录原因，绝不机械删除凑 70%。
- 受测试限制，本轮未连接真实生产 Redis 或向真实 LLM 发 POST；运行行为须部署重启后才会生效。未得到当前请求的 git 提交/推送授权。

## 第二轮 Code Review 修复补充（2026-10-22）

- 用户允许 F1 的 LLM 合并判断误差，也允许 F2 的 HTTP 底层连接重试，不关闭这些功能。未压到 70% 仅 `logger.warn`，不发第二轮业务压缩 POST。
- S1：实时 `applyFact` 与压缩 `applyCompressionPlan` 共用同作用域 Redis SET NX 锁，LLM 模型请求不持锁；执行时继续核验历史快照。锁有租约，不是跨多键绝对事务，其他管理清理入口未全部锁定。
- S2：用 SCARD 对索引先做无假阴性预筛，只有可能超过阈值时才加载完整历史并排除 inactive/已过期事实。

- F3：为模型提供证据数量、不同发送者数、群数和最后证据时间的摘要，不传证据正文。
- F4：原群级提炼请求中的历史记忆按本片发言人与话题相关性选择，预算不足时保留相关事实优先于短字符串。
