## 最新方案：95% 触发独立压缩请求（2026-10-22，覆盖下文旧 80% 方案）

- **保留群级批量提炼**：凌晨 4 点仍按授权群→自然日→Token 分片提炼，不对每个参与聊天的成员另行发 POST。普通写入的同键同值存储去重依然全时生效；Q5 要求的跨键语义去重可在**原有提炼请求**附带相关旧记忆完成，不以压缩阈值为条件，也不单独发 POST。
- **只在超过 95% 时额外调用**：日提炼完成后，服务端从 Redis 读取每个**独立记忆作用域**的未过期 active 数量；仅当 `count > cap * 0.95` 时，为该作用域创建**一次独立夜间压缩任务**，依预算可能产生多个分片 LLM POST，模型只审阅该主体/作用域已有事实并提出存量压缩计划。未超过 95% 时不得增加额外压缩 POST；已确认 Q11 仍适用：即使当天没有群聊，只要超过 95% 也应夜间整理。不同用户、不同群各自独立；跨群个人 `user` 按 UID 去重，不因加入多个群而多发请求。
- **目标压缩至容量的 70% 及以下**：LLM 自主识别语义重复并提出保留、合并、归档列表；目标剩余有效记忆数 `<= floor(cap * 0.70)`。不能简单按 importance 或时间倒序删除，优先保留具体、独特、有证据的长期有用事实。现有模型取舍与存储权限校验、归档优先、保留证据、避免跨主体合并及失败不强删的安全约束仍适用。仅模型给出充分理由且服务端复检通过后执行；无法安全压到目标时允许本次不足额并保留已有事实，不能回退分数淘汰。
- **个人与群公共配置分离**：`maxMemoriesPerUser` 对 `user` 与 `user_group`，**默认 100**（源码已是 100），Guoba `InputNumber.min = 50`；新增 `maxMemoriesPerGroup` 对每群公共 `group`，**默认 50**、Guoba `InputNumber.min = 20`，在个人配置项正下方显示。不改变 `memoryContextLimit` 召回逻辑，不以新群公共值触发全量召回模式。原有磁盘配置中已显式保存的旧个人数值由现有加载规则保留，除非用户手动调整；Guoba min 是 UI 约束，不是迁移旧值的指令。
- **阈值例子**：个人上限 100 → 数量 95 不触发、**96** 触发、目标 **70**；群公共上限 50 → 数量 47 不触发、**48** 触发、目标 **35**。比率严格大于 0.95，不是 >=。
- **实时超额保留**：智能对话实时 `Memory_Tool` 写入允许超过各自容量，不做实时压缩，不插入实时维护 System Prompt，不按评分直接淘汰；凌晨压缩模型使用既有 `memoryGroupCapture.provider`，失败时旧数据保留。过期清理依旧与 LLM 无关。
- **对旧设计的替换声明**：本节取代下文 Q7 的「80% 提炼模型额外提示」和 Q8/Q9 的「在原提炼调用里做主动旧记忆压缩」；取代 Q11「仅超过 100% 才独立夜间处理」的阈值，以及群公共沿用 `maxMemoriesPerUser` 的决定。Q3～Q11 其他事实、安全要求仍保留。**不得再次把 80% 提示加到实时聊天或夜间提炼中。**
- **API 成本语义**：常规提炼 POST 数仍由授权群日窗口和分片决定；新增压缩任务数约等于当晚 **>95% 的独立作用域数**，实际 POST 数为任务的分片数之和（包括无原文的作用域），不是总成员数。失败重试若立即追加，实际 POST 可能更多；首版推荐每次定时运行每个作用域最多尝试一次，失败留待下次定时任务。不要隐式增加每天全成员压缩 API 调用。
- **当前实施状态（2026-10-22）**：用户已授权并实现 Code Review 推荐：实时保存允许超额；凌晨严格 >95% 才为每个作用域创建独立压缩任务，超预算时随机分片逐片 POST；目标 <=70%；每个作用域同一个北京时间自然日最多一次请求，即使未达 70% 也只记 `logger.warn`，不二次 POST；模型错误不强删；归档操作校验 ID、主体/群/作用域、完整快照及 manual 保护，原始证据保留。通常跨键语义去重在原群级提炼 POST 内尽力执行（每片历史预算 8000 字符），存储层精确去重不依赖阈值。后续部署仍须真实 Redis/LLM 链路验收；不操作真实生产数据，不自动提交/推送。

## 实现策略与不变式

1. 对话阶段先用 `MemoryStore.listRecallCandidates(subjectId,groupId,{excludeUser})` 完成既有主体/权限/过期筛选，保持私聊、群聊、@他人权限边界。只有授权候选能出现在 LLM 入参；LLM 输出仅允许指定候选的列表索引，服务端校验且去重、截断数量，绝不写入记忆库。
2. LLM 调用使用 `SubLLM` 已配置 Provider ID，不额外添加 API 接入；新字段 `memoryRecallProvider` 缺省空串表示关闭。provider 引用参与统一的配置校验，未解除引用前不可删除条目；保存后即时生效。
3. LLM 模式尽量保留旧版常驻画像最多 2 条，其余按模型输出选最多 `memoryContextLimit` 条；模型返回合法空列表时仅注入常驻画像；参数不合法或调用失败时回退旧版匹配。为降低提示注入风险，候选和问题以不可信数据 JSON 传入，模型只返回结构化索引。
4. **全量模式优先级最高**：不论是否选择 LLM，都不发起额外 LLM 请求、不做关键词过滤。该模式允许完整导入记忆文本，而不是沿用旧版 1500 字截断，**（2026-10-23 废止：全量模式已删除，注入也不再按字符截断）**
5. **当前结构限制（按最新配置澄清）**：`maxMemoriesPerUser` 只约束个人 `user` / `user_group` 的容量目标，不限制总对话候选数；`maxMemoriesPerGroup` 默认 50，群公共 `group` 的 95% 夜间压缩已实现。全量召回已删除，注入条数恒 ≤ `memoryContextLimit`。**（2026-10-23 废止：全量模式已删除，注入条数恒 ≤ memoryContextLimit）**
6. 对话召回、每日提炼、语义去重与容量管理均已实现（落地细节见 `plan.md` 的「实际落地说明」），仍待真实 Redis/LLM 链路验收。Q10 明确实时 Memory_Tool 可以临时超额，`maxMemoriesPerUser` 对实时写入不作为硬拦截。此决策不改变已确认的对话召回规则。

- **群公共记忆容量**：个人 `user`、每群个人 `user_group` 和每群公共 `group` 都独立复用 `maxMemoriesPerUser` **作为凌晨整理容量目标**。如配置 50，每个作用域夜间整理后目标不超过 50，但 Q10 允许实时期间暂时超过；失败时不强删，需记录超额未完成状态。不新增配置项；修改锅巴标签/帮助文案说明这不是实时硬上限。当前 group 不受存储上限约束，目标行为尚未实现。
- **过期记忆当前行为，无须模型读到历史记忆**：`validTo` 为有效期截止的记忆，过期后立刻从 `listRecallCandidates` 排除、`_countActiveByScope` 不再计入配额； 凌晨任务 `DailyConsolidation.runDaily()` 末尾调用 `MemoryStore.deleteExpired(30)`，在截止时间超过 30 天后才物理删除 active 项；archived 项同样按宽限规则清理。清理是 Redis 侧规则，不需要 LLM 或历史提示词，不受 80% 阈值影响。日任务未能执行到清理阶段时无法保证准点物理删除。
- **现有模型输入边界**：`processWindow()` 读取当天原文 `rows`，传 `runExtraction`，只将 `EXTRACTOR_SYSTEM` 和 `buildExtractionPrompt` 传给 SubLLM；它看不到旧记忆列表。`applyCandidates` 已支持同作用域同键同值证据并集、同值强化、单值冲突替换、明确否定的 `retract`，不支持不带新消息证据的跨键任意语义合并或按重要度删除。达到 100% 的 `_evictLowest` 会永久删最低重要度项且没有明确排除 `manual`；必须确定保护策略。**（2026-10-23 现状：提炼 POST 已带「历史记忆对照」；`_evictLowest` 已删除，容量改由 >95% 的独立压缩任务整理）**
- Q3～Q11 为历史决策，其中涉及 80% / 统一容量配置 / 原群提炼内主动压缩的内容已经被本文件最前方 **95% 独立压缩方案**取代。最新实施步骤见 `.scratch/memory-llm-recall/plan.md`；自动压缩与实时允许超额写入均已实现，容量整理仍须真实链路验收。
