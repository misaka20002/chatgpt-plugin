# 撤掉自主回复的工具禁用开关

Status: ready-for-agent（2026-10-28 定案：Q1 恢复工具、Q2 保留 Core 参数、Q3 不通知）

## Problem Statement

锅巴「群聊自主回复」下面有一个「自主回复禁用智能模式工具」开关，默认开着。它的存在等于把「自主回复能不能用工具」当成部署配置来管，而实际想要的是让自主回复像人一样说话——能查、能办、能记住。开关在这个位置上只会让同一套行为在不同机器上不一致，也让「自主回复为什么不替我干活」变成一个需要翻面板才能解释的问题。

## Solution

删掉这个开关和它的一圈接线。自主回复的正式回复回到 `af3bd8f` 之前的行为：按当前智能模式与 provider 配置装配工具。Core 里按次压制工具的通用参数保留原样——它是 Core 的能力，不是这个开关的私有实现。

## User Stories

1. 作为群里的普通成员，我希望机器人自主接话时也能真的帮我查东西、办事，而不是只会说话。
2. 作为部署者，我打开锅巴不会再看到一个需要我判断「该不该让机器人用工具」的开关。
3. 作为部署者，我不会因为别人的机器上关过这个开关，就得到和对方完全不同的自主回复行为。
4. 作为部署者，我升级后不需要做任何操作，行为自然回到「按智能模式配置使用工具」。
5. 作为维护者，我不会在两处（Core 与群聊配置）看到同一个概念的两个开关。
6. 作为维护者，我读 `apps/chat.js` 时看到的自主回复选项只有它自己的上下文设置，不夹带工具策略。
7. 作为维护者，我仍然可以在 Core 层按次压制工具——那是协议层的能力，和群聊配置无关。
8. 作为维护者，我翻到 `af3bd8f` 那起事故时，能在 ADR 里读到为什么当天又撤掉，而不是靠猜。
9. 作为排查线上问题的人，我知道「自主回复调了 Memory_Tool」现在是预期行为，而不是 bug。
10. 作为后来者，我不会在代码里找到只被一条测试引用的 `groupReplyToolsDisabled()` 这种一层转发函数。

## Implementation Decisions

- 删除锅巴面板里的该开关；同分栏的「开启群聊自主回复」「自主回复群」等字段不动。
- 从群聊配置归一化里删除该键。老配置里的残留键变成无人读的死键，不做迁移、不做提示。
- 删除只做一层转发的取数函数，调用点直接恢复成只带 `groupAutoReply` 与上下文设置的选项对象。
- **保留** Core 的 `opt.disableTools` 通用参数与四条 provider 链路上的分支：它早于这个开关存在（`0787c03`），是协议层「按次压制工具」的能力，删掉会连带改变 Claude/Responses 原生工具与 Gemini 搜索/代码执行的开关语义。
- 运行时指南里那段「专用关停」的说明恢复成描述现状：正式回复按现有智能模式与 provider 配置使用工具。
- 新增一条 ADR 记录这次同日反转：上午因 Memory_Tool 写记忆加闸，晚上因「更像人」撤掉，以及接受副作用这件事。

## Testing Decisions

- 缝沿用现有的 `chatgpt_for_firstperson_call → Core.sendMessage` 选项断言：它已经在验证自主回复传给 Core 的 options，本次只是让断言回到「没有工具策略」这一事实。
- 删除「工具禁用可由开关单独放开」的整条用例：它测的开关不存在了，留着只能测空气。
- 保留 Core 层「显式禁用本地和内置 tools」的用例：Core 的参数还在，那条用例覆盖的是 Core 的能力。
- 面板断言删掉后不再补替代断言：面板少一个字段没有可断言的对外行为，靠人眼看一次。
- 好测试的标准沿用本仓既有口径：只断言对外契约（传给 Core 的 options、落盘结果、回复文本），不测内部调用次数与顺序。

## Out of Scope

- Core 的 `opt.disableTools`（保留，当前没有生产调用方）。
- 给自主回复单独做工具白名单或「只禁写类工具」——需要工具分类，另议。
- 通知已经手动关过开关的部署者（Q3 明确不管）。
- 清理老 config.json 里的残留键。
