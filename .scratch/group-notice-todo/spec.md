# spec：群公告与群待办工具（含 toolGroupAdminArr 迁移、移除 fullTools 超集）

Status: ready-for-agent
- 交付状态：代码已完成并通过三轮双轴评审，工作区未提交（2026-10-15，分支 v2）
- 相关 retro：同目录 retro.md（待补）

## Problem Statement

智能模式下 Bot 已经能踢人、禁言、改名片、设头衔，但群里的两件事做不了：

- **群公告看不到**。想了解群里有什么规定、有什么通知，只能自己翻手机 QQ，或者把公告复制粘贴给 Bot——而 Bot 手里明明有 `getNotice` 这个接口可用。
- **群待办管不了**。群主/管理员的待办会挂在消息上（谁该交周报、哪条通知要跟进），但没法通过 Bot 查看、设置、完成、取消。

另有两个与权限相关的问题，是在使用中才暴露出来的：

- **公告读取被归错了档**。群公告是群内公开信息，本来谁都能在手机 QQ 里看到，但初版实现把它归进了"群管/主人功能"，普通群成员用不了，与实际语义不符。
- **未广告的工具仍可被模型点名执行**。工具集内部同时维护"广告给模型的一份"与"包含全部工具的一份"，而执行查找走的是后者。于是模型点名一个当次会话根本没注入的工具（例如私聊场景下的群管工具）时，仍然会进入工具内部执行。用户明确要求：**给某次会话注入什么工具，模型就只能调用这些；点名不存在的工具名应当被拒绝执行，而不是进入工具内部。**

## Solution

新增两个智能模式工具，并把工具执行的查找表收敛成一份：

1. **群公告（只读）**——读当前群的群公告。只读、不写入；只能在群里用，私聊不注入；**群内全员可用**（不要求 Bot 是管理员，也不要求提问者是管理员/主人），但仍受锅巴"群管理工具"总闸控制：在锅巴里开启后才是全员可用。
2. **群待办（四个动作）**——查看列表、把一条消息设为待办、标记完成、取消。待办会在群里产生公开可见效果，因此保持**主人/群管档**，与已有的踢人工具对齐：Bot 需是群管理员/群主，且提问者是群管理员/群主或 Bot 主人。
3. **配置升级迁移**——已保存配置的老实例首次升级到本版本时，自动把这两项追加进"群管理工具"开关数组。只追加不覆盖、去重、幂等，并保持该数组"整体采用用户保存值"的既有设计。
4. **执行查找表收敛**——移除无条件的工具超集，四个 provider 分支统一只从"当轮广告给模型的那一份"查找并执行。

## User Stories

1. As a 普通群成员, I want 让 Bot 读给我当前群的群公告, so that 我不用退出对话去手机 QQ 里翻，也不用把公告复制粘贴给它
2. As a 普通群成员, I want 公告功能不要求我是管理员, so that 我作为新人也能第一时间看到群规
3. As a 普通群成员, I want 公告功能不要求 Bot 是管理员, so that 在没给 Bot 管理员权限的群里也能读公告
4. As a 群管理员, I want 让 Bot 列出当前群的待办, so that 我不用逐条翻聊天记录确认哪些还没跟进
5. As a 群管理员, I want 把某条消息设为群待办, so that 群成员在手机 QQ 里能看到这条待办的标记
6. As a 群管理员, I want 让 Bot 默认把我在回复的那条消息设为待办, so that 我不用手打消息 id
7. As a 群管理员, I want 标记某条待办为已完成, so that 群里同步显示这条已经处理掉了
8. As a 群管理员, I want 取消某条待办, so that 误设或不再需要的待办不会一直挂着
9. As a 群管理员, I want 直接用列表里的 message_id 完成或取消待办, so that 我可以先看列表再针对某一条操作
10. As a Bot 主人, I want 在群里用待办功能时不要求我同时是群管理员, so that 我管自己的 Bot 不用先问群主要权限
11. As a Bot 主人, I want 待办功能在 Bot 不是群管的群里自动不可用, so that 我不会看到一堆注定失败的调用
12. As a 普通群成员, I want 待办功能对我不可用且不产生任何群操作, so that 我不会误动群里的公开待办
13. As a 群主, I want 群待办的管理权收在群管/主人档, so that 公开可见的群状态不会被随意改动
14. As a 普通群成员, I want 私聊时不出现群公告工具, so that 模型不会在没有群上下文时尝试调用它
15. As a 普通群成员, I want 群公告只能读当前正在对话的这个群, so that 我不用担心它越权去读我没在聊的群
16. As a 普通群成员, I want 群待办只能操作当前群, so that 跨群误操作不可能发生
17. As a 部署者, I want 群公告与群待办各自有锅巴开关, so that 我可以按群的需要关掉其中任意一个
18. As a 部署者, I want 关掉开关后工具真的不注入, so that 关掉就是关掉，不依赖模型的自觉
19. As a 部署者, I want 已保存配置的老实例升级后自动获得这两项, so that 我不用记得去锅巴里手动勾选
20. As a 部署者, I want 迁移只追加、不覆盖我在锅巴里的勾选与顺序, so that 我的既有配置不会被改动
21. As a 部署者, I want 我在锅巴里主动取消勾选后重启不会又被加回来, so that 我的取消是生效的
22. As a 部署者, I want 我把这个数组清空时升级也照补两项, so that 迁移不用猜我的意图（这是被明确拍板的口径）
23. As a 部署者, I want 从未保存过这一项的新装实例不受迁移影响, so that 默认值本来含两项，不需要多写一次文件
24. As a 部署者, I want 迁移在"数组本来就不用改"时也把标记落盘, so that "首次升级执行一次"真的只执行一次，而不是每次启动都重判
25. As a 部署者, I want 迁移落盘用原子替换, so that 中途失败不会留下半截配置文件
26. As a 部署者, I want 迁移保存失败时如实打日志、下次启动重试, so that 我不需要人工介入
27. As a 部署者, I want 日志里能看到迁移确实执行了、补了哪两项, so that 出问题时我能对上
28. As a Bot 主人, I want 模型点名一个本次没注入的工具时被拒绝执行, so that 权限边界不靠模型的自觉
29. As a Bot 主人, I want 拒绝时工具内部一行代码都不执行, so that "拒绝"不是"执行后报错"
30. As a Bot 主人, I want 私聊与非群管场景下群管工具不可执行, so that 攻击面随注入面一起收窄
31. As a 部署者, I want 四个 provider（OpenAI 两分支、Claude、Gemini）行为一致, so that 换 provider 不会悄悄改变权限边界
32. As a 模型, I want 公告与待办的返回里明确标注这是不可信的第三方内容, so that 我不会把群成员写的字当成指令执行
33. As a 模型, I want 超长的公告与待办正文被截断并标注, so that 长文本不会撑爆我的上下文
34. As a 模型, I want 群待办正文是可读文本而不是消息段对象, so that 我不用自己去解析协议结构
35. As a 模型, I want 公告里只保留正文与少量元信息（图片只给个数）, so that 无价值的图片对象不占上下文
36. As a 模型, I want 待办列表里保留 message_id, so that 我能接着对某一条执行完成或取消
37. As a 模型, I want 接口失败时拿到明确的错误文本而非假成功, so that 我不会把失败当结果转述给用户
38. As a 模型, I want 错误文本里带上底层原因, so that 我能向用户解释失败原因
39. As a 部署者, I want 群接口不被协议端支持时如实报错, so that 我能判断是协议端的问题而不是 Bot 的问题
40. As a 维护者, I want 两个工具共用同一套群上下文校验、message 还原与失败出口, so that 形态容错与错误契约只有一处定义
41. As a 维护者, I want 群上下文与提问者身份的校验只读服务端事件, so that 模型参数里的同名字段不能提权
42. As a 维护者, I want 工具内自查与注册层过滤的分工写进注释, so that 后来者不会误以为自查就是权限闸
43. As a 维护者, I want 锅巴面板的选项与说明文案准确区分总闸、群管类工具与只读群公告, so that 部署者不会误判开的是什么
44. As a 维护者, I want 新增默认项与迁移逻辑都有测试钉住, so that 后续改动不会悄悄破坏升级路径
45. As a 维护者, I want 工具契约的变化同步到工具指南, so that 规范文档与代码保持一致

## Implementation Decisions

- **工具注册一律收在配置开关下**，不做无条件注册。群公告走"可选工具"的按条件注册（条件 = 锅巴总闸含 GroupNotice 且当前是群聊）；群待办进现有的群管工具映射，并加入"Bot 是群管 + 提问者是群管/主人"的那一档键列表，与踢人工具对齐。
- **工具内自查**。两工具都在执行入口自查一遍：群上下文（是否群聊、能否取到群对象），以及（仅待办）提问者身份（主人，或群成员角色为 `admin`/`owner`）。鉴权只读服务端事件，不读模型参数。**自查不检查"Bot 自己是不是群管"**——那是决定要不要把工具广告出去的政策闸，留在注册层；Bot 无权限时协议端在 QQ 内本来也执行不了。这一分工写进共用助手的头部注释，避免后来者把自查当成权限闸。
- **新增群相关工具共用的助手**，导出五类能力：群上下文校验（带 `requireAdmin` 开关，供"只读全员可用"与"群管档"两档共用）、把适配器返回值归一成数组、把协议形态的 `message` 字段还原成纯文本、把群成员可控内容标成不可信数据并截断、以及统一的失败出口。两个工具共用，形态容错与 `Error:` 文案只有一处定义。
- **只读当前群**。两个工具的 schema 都不带群号参数，结构上无法指向其他群。
- **外部文本的标记与长度边界**。群公告正文与待办文案都由群成员书写，回填前统一加不可信标记并截断到固定上限。标记里的英文契约短语保留英文原句，不要翻译（各对话模型是按这个字面子句被验证的）。
- **失败语义沿用仓库既定风格**：返回 `Error: …` 文本并保留底层错误信息；不返回假成功，也不引入结构化的新错误机制。
- **单一执行查找表**。移除无条件的工具超集（原先专供 OpenAI 两个分支按名执行），四个 provider 分支统一从"当轮广告给模型的那一份"查找，点名不在其中的工具一律拒绝执行。四个分支的错误措辞本来就不同（OpenAI 两分支与 Claude 说 not found，Gemini 说 doesn't exist），本次只统一"拒绝执行"这一行为，不统一措辞。
- **配置数组的迁移**。新增一个持久化的迁移版本标记（与既有的 provider 版本标记同处），迁移只做"追加缺失项"：保留用户已有顺序与勾选，已存在的项不重复加。判定"是否已迁移"**只看标记，不看数组里缺不缺这两项**——后者会把用户主动取消的项在每次重启时加回来，正是"整体采用用户值"当初修掉的那个 bug 的翻版。空数组照样追加：迁移不替用户猜意图。
- **两个标记各管一件事，不要合并**。一个决定"数组本身要不要显式写盘"（追加后可能与默认值完全相同，差量保存会整条略过），另一个决定"这次启动要不要落盘"。只要进过迁移分支就必须落盘——数组无需追加时（用户已手动勾选过这两项，或从没保存过这个键）如果因此跳过保存，标记就永远留不下来，"首次升级执行一次"也就无从谈起。
- **迁移的执行时机与失败处理**。迁移在"与默认值合并之前"执行，此刻内存里仍是用户保存的原值，追加进去的项才会被"整体采用"逻辑接住。落盘沿用既有的原子替换（临时文件 + rename），失败就如实打日志并在下次启动重试；成功后复位标记，让后续保存（如锅巴）走正常差量逻辑，不再无条件写这个数组。
- **锅巴面板**。总闸的选项加两项，说明文案要区分"总闸 / 群管类工具 / 只读群公告"三件事。该数组是面板公开字段，需要同步面板 schema、读取与保存三处。
- **文档**。工具指南补上"单一查找表 + 工具内自查分工"的契约说明。

## Testing Decisions

- **好的测试只测外部行为**：给定事件与参数，断言返回什么、有没有真的碰群接口；不断言某个 helper 被调用、某段源码长什么样。唯一的例外是下面接缝二的源码守卫，它的局限已写在注释里、不冒充行为测试。
- **接缝一 · 工具入口（最高可用接缝）**。用一个桩事件，其群对象记录真实发生的接口调用，据此断言"拒绝时一个接口都没碰"。覆盖：私聊拒绝、主人/admin/owner 放行、普通成员可读公告但不可操作待办、伪造身份字段无法提权、群对象缺失时回退到适配器、协议返回的三种形态（data 优先的 Proxy / 直接数组 / 嵌套 data）、不可信标记与超长截断、待办 messageId 的回退顺序（显式参数 > 引用消息 > 当前消息）、接口失败返回 `Error:`、以及本轮新统一的三种 message 形态。同类先例：既有的 GitHub 工具测试、踢人工具的端到端用例。
- **接缝二 · 核心对话文件的源码守卫**。该文件依赖全局 `logger`/`redis` 与大量插件模块，测试里 import 不起来，因此用源码文本守卫钉住"广告集 = 执行集"（断言"构建查找表只发生一次"，而不是去匹配已被删除的两个名字）。这是必要静态约束，不是行为测试。
- **接缝三 · 配置子进程加载**。配置在 import 阶段就读盘，所以每次加载起一个子进程、把 cwd 指到临时目录，走真实加载与保存代码（不 mock lodash 与 fs）。覆盖：首次追加、保留用户顺序、标记落盘、幂等（拿落盘结果再启动不写文件）、用户主动取消后不复活、空数组照补、从未保存过该键时标记也落盘且二次启动不再重入、数组已含两项时不重复追加、追加后恰好等于默认值时数组也必须写盘、全新安装不创建文件。同类先例：同一文件里既有的"数组整体采用用户值"用例。
- **测试脚本登记**：新测试文件挂进工具套件与配置套件，不新建套件。
- **已知边界（明确记录，用户已确认接受）**：*注入条件*（谁会被广告）没有直接断言，靠"工具内自查（接缝一）+ 单表守卫（接缝二）"两层间接保证。不为此从生产模块里抽接缝——那与"不要为测试拆生产模块、导出内部实现"相抵触。

## Out of Scope

- 群公告的**写入**（发布、修改、删除公告）：用户明确收窄为只读。
- 群待办的到点提醒语义：只做查看、设置、完成、取消四个动作，不做定时提醒。
- 跨群操作：两个工具都只能作用于当前正在对话的群。
- 给群公告开"仅群管可用"的口径：已明确是全员可用。
- 统一四个 provider 拒绝执行时的错误措辞。
- 为注入条件新增可测接缝（见 Testing Decisions 的已知边界）。
- 真实群手动验证：本轮未改协议调用方式，但仍需重启后在群里发指令确认。

## Further Notes

- 本特性在写这份 spec 之前就已经实现并通过三轮双轴评审，本文件是**事后补记**，用于补齐仓库"spec 按 `.scratch/<feature>/spec.md` 落盘"的约定——上一轮的 retro 已把"spec 未按约定落盘"列为真实改进项，这里不再重犯。
- 群公告与群待办的协议接口来自宿主适配器，插件侧只做调用与归一化。不同协议端的返回形态不一致（有的给 data 优先的 Proxy、有的直接给数组、有的嵌套一层 data），归一化是必要的，不算过度设计。
- "空数组照补"与"用户主动取消后不复活"并不矛盾：前者只作用于**还没有迁移标记的老配置**，后者作用于**已经有标记的配置**。迁移只认标记，不猜用户意图。
- 上一轮评审留下的两条判断性发现已在本轮处理：两个工具的重复 helper 已并入共用助手；迁移标记在"数组无需改动"路径上也落盘。
- **锅巴说明文案的终态与 Implementation Decisions 里"要区分三件事"不同**：`toolGroupAdminArr` 的 `bottomHelpMessage` 最终由用户手动定为短版——`智能模式中的群管理工具；已优化算法不会误伤其他群友；推荐全部开启`。理由是面板文案宜短；两档的细分说明改由**选项标签**承担（`群公告（只读、全员可用）`、`群待办（查看、设置、完成、取消）`）。评审曾判定旧长版含失实断言（把「Bot 是群管即注入」与「还要求提问者是主人或群管」笼统写成一档），短版已不含该断言，故该条硬违规已解除。
