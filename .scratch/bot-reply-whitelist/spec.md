# Bot 响应白名单：多号/多适配器时只让指定账号答话

Status: done

## Problem Statement

多开 QQ、或 QQ 与微信／Satori／OneBot 等其他适配器共存时，同一个群里的多条 Bot 账号会同时收到同一条消息，各自走一遍对话链路。用户看到的是：@ 了 A 号，B 号也可能因为「第一人称呼叫」或「群聊自主回复」而答话，一个群出现两条回复、烧两份 token。

插件里没有任何账号级开关能收住这件事。「对话白名单／黑名单」管的是提问者与群；`trssBotUin` 只影响取 uin，不参与准入；按 bot 放行的函数只有角色动图一处，只管出图。

## Solution

锅巴新增配置项「Bot 响应白名单账号」（`botReplyWhitelist`）：

- **留空 = 所有账号都响应**，与今天的行为完全一致，老配置升级后无感。
- **非空 = 只有列表内的账号（`self_id`）响应对话触发**；列表外账号在对话链路上静默。
- 候选来自所有已注册适配器下的账号，并允许直接输入尚未登录的账号。

## User Stories

1. 作为同时挂两个 QQ 号在同一个群的部署者，我希望只有指定的那个号答话，这样群里不会出现两条一模一样的回复。
2. 作为挂了 QQ 与微信两个适配器的部署者，我希望按账号而不是按适配器决定谁说话，这样一个适配器下有两个号时也能只留一个。
3. 作为已有的单号部署者，我什么都不配置，行为必须和升级前完全一致。
4. 作为部署者，我希望白名单留空时是「全部响应」而不是「全部不响应」，这样清空列表就是一个安全的回退动作。
5. 作为部署者，我希望被静默的账号仍然能收到「我为什么没回」的线索，而不是只能猜。
6. 作为部署者，我希望非白名单账号上 @ 机器人时，插件不去调模型，别为一条注定不回的消息付费。
7. 作为部署者，我希望群聊自主回复也受同一份名单约束，否则关掉直接应答后它仍会抢答。
8. 作为部署者，我希望 `#chat1`／`#chatglm`／`#claude`／`#gemini` 这些其他模式同样受约束，不要留一个绕过的口子。
9. 作为部署者，我希望白名单不影响 `#结束对话`、`#gpt偷图`、meme、戳一戳这些非对话入口，这样我在非白名单号上仍然能排障。
10. 作为部署者，我希望白名单不影响已经建好的定时任务，昨天设的提醒今天照响。
11. 作为部署者，我希望主人身份也不豁免——否则主人同时 @ 两个号时，非白名单号仍会回一遍。
12. 作为部署者，我希望先配好白名单再上号也能成立：还没登录的账号必须能填进去，也能在面板里看到。
13. 作为部署者，我希望在锅巴里看到每个候选账号挂在哪个适配器下，多号时不至于认错。
14. 作为后来接手的人，我希望「取不到账号身份时放行」这条写在代码注释与决策记录里，不要被当成漏洞「修」成拦截。
15. 作为维护者，我希望判定逻辑只有一份、可单测，而不是散在四个入口各写一遍。

## Implementation Decisions

- **匹配单位是账号 `self_id`**，统一转字符串比较（微信适配器可能出现 `wx_xxx@im.wechat` 这类非数字标识）。配置项为数组，默认空。
- **判定集中在一个 util 的两个导出**（`utils/botReplyWhitelist.js`）：`eventBotId(e)` 负责取账号（`self_id` → `bot.uin` → 空串），`isBotReplyAllowed(e, { label, silent })` 负责放行/拦截与日志。入口只调用，不各自判断。
- **空列表与非数组都按「未启用」处理**；列表里的空字符串与纯空白条目会被丢弃。这样手工改坏的配置最坏是「白名单不生效」，而不是「整个插件静默」。
- **取不到账号身份时放行（fail-open）**，并记录一条说明。单号部署、宿主自造影子事件等路径可能没有可信 `self_id`；反过来拦下的代价是整插件静默。这条只覆盖直接对话与第一人称两条入口——自主回复的准入沿用既有的「取不到账号就不准入」前置，到不了 fail-open。
- **闸门放在入站侧，不放抽象对话层**：抽象对话层是所有回复路径的汇合点，定时任务也经过它，放在那里会连定时任务一起掐掉。四个入站点是直接对话、第一人称呼叫（含自主回复）、`otherMode`、自主回复的候选准入。其中 `otherMode` 目前没有 rule 接线（`#chat1`／`#chatglm`／`#claude`／`#gemini` 已不挂规则，也没有按钮派发），闸门留在那里只为这些入口哪天恢复时不必再补，不算当前生效的覆盖面。理由与替代方案见 `docs/adr/0011-bot-reply-whitelist-cut-point.md`。
- **自主回复在候选准入处拦**，不等到发送前：名单外的账号连判断都不跑，省一次注定白跑的模型请求。
- **准入处静默、入口处留痕**：候选准入对每条群消息都会执行，逐条打日志会刷屏；日志只留在三个显式入口，用 `logger.info`，带账号与触发入口。
- **锅巴控件用自由输入的多选下拉**（`Select` + `mode: 'tags'`）：只用下拉的「允许新增」属性不足以让用户手填，`tags` 模式才真正接受任意输入。
- **候选在打开面板时现算**：遍历宿主所有已登录账号，标签写成 `账号（昵称｜适配器名）`；已保存但当前不在线的账号补一行 `（当前未登录）`，避免面板把离线账号当脏值丢掉。
- **保存时归一化**：去空白、丢空项、去重。清空即回退为「全部响应」，不需要额外开关，也不需要配置迁移标记。

## Testing Decisions

- 好的测试只钉外部行为：给定一份名单与一个事件，回答「这个账号该不该说话」，以及被拦下时有没有留下线索。不测函数内部如何取值、不测日志字段的完整措辞。
- 被测模块是判定 util 本身，覆盖五条路径：空名单放行、命中放行、未命中拦截、`self_id` 缺失回落到 `bot.uin`、取不到账号时放行。
- 三条边界一并钉住：配置里存成数字也命中、列表只含空白条目按未启用、非数组按未启用。这三条都是「手工改 config.json」的真实场景。
- 日志用「有没有写、有没有带账号」来断言，不做逐字快照——措辞会变，行为不该变。
- 测试直接替换内存里的配置，不落盘；配置在 import 期从磁盘读取，所以测试文件用 `globalThis.logger` / `globalThis.redis` 桩隔离宿主依赖。
- 先例：同一套件里的配置类测试（`test/configArrayMerge.test.js`、`test/configBaseUrl.test.js`）也是「加载真实配置代码 + 桩宿主全局」。

## Out of Scope

- **出站路径**：定时任务回放、主动打招呼、工具箱 OTP 与代发。它们不是「对当前这条消息的响应」，收进来会改变既有语义。
- **非对话入口**：`#结束对话`、`#gpt偷图`、meme、戳一戳观察器、记忆采集。
- **主人豁免**。
- **「账号 + 群」二维白名单**：群维度已有自主回复与角色动图两套授权表。
- **修复 `getBots()`**：它把适配器实例当账号去索引，是既有缺陷，与本功能无关。

## Further Notes

- 白名单非空时，被挡账号上每条点名消息都会打一条 `logger.info`；该级别不落文件，活跃群会让 stdout 变吵。真嫌吵就降成 debug 输出，判定逻辑不用动。
- 被挡消息若同时含 AI 第一人称，`chatgpt()` 与 `chatgpt_for_firstperson_call()` 会各打一条：loader 在规则返回 `false` 后继续匹配同插件的下一条规则。两条都不落文件，量级只与「含第一人称的被挡消息」相关。
- 宿主的 `accept` 阶段不能当闸门：返回 `"return"` 会终止整条消息链，连其他插件一起掐掉。这条已写进 ADR，避免后来者再试一次。
