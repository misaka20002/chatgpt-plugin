# 02: 本地地图能拍成一张可检索的表

**What to build:** 把所有已缓存的地图拍平成条目表，一条指令一条，字段够查询工具、提示词与代执行用（插件名、插件一句话、写法、关键词、说明、风险档、权限位、参数、示例）。完成后，给定本地地图目录，调用一次就能拿到全部条目与统计。

**Blocked by:** 01

**Status:** done

- [x] 一份地图的每条指令产出一条条目，条数与地图一致（多份地图时相加也对得上）
- [x] 条目的插件名取地图里的展示名；缺展示名或展示名是空白串时退回 key
- [x] 关键词含写法本身、标题、别名、关键词字段，去重后不为空
- [x] 插件一句话（`plugin.summary`）进条目，提示词不必再读一遍地图
- [x] 风险档只认 `q/w/a`；缺失或写了不认识的值按最危险的一档算
- [x] 没有 `command` 的条目被跳过（那类不是可执行写法）
- [x] 空目录、损坏的 `entry.json`、schema 不对的旧文件、解码不了的目录名都不抛错，只跳过那一份
- [x] 返回统计里的插件数与条目数对得上

## 落地

`loadEntries()` 与 `listLocalPlugins()` 加进同一个文件。条目字段固定为 17 个：
`plugin / pluginKey / pluginSummary / command / keys / description / what / risk / permission / args / ex /
preconditions / pitfalls / failures / edgeCases / timing / cost`。
查询、提示词、代执行都只认这一张表，不必各自再读一遍地图——后六项是「该不该用、用了会怎样」
的依据，也是地图相对「读插件源码」的独有价值（第三轮评审指出原先只留 10 个字段，把坑与失败
表现丢了，已补回）。

存储是**单文件**：`maps/<encodeURIComponent(key)>/entry.json`，形如 `{ meta, map }`。
地图与元信息同一次 rename 落盘，不会出现「新地图 + 旧版本号」这种同步永远追不上的错位。
读取入口只有一个 `readEntryAt(segment)`，列表与展开共用同一次读，坏文件不会读两遍报两次日志。

没有写法的条目直接跳过——「任意含某词的消息都会触发」这类检索不到、也代执行不了。
关键词 = 写法 + 标题 + 别名 + 关键词字段，去重（写法必须在内，用户照原样敲也要查得到）；
参数拼成一句话（必填不带括号，可选用方括号，附示例）。

风险档收窄的意义：缺字段的地图被当成 `q` 就等于把未知指令放进「查询也安全」那一档，
代执行会照着放过去。按 `a` 算，最坏结果是多问用户一次。

测试 10 项（连同 01 共 21 项；最终三份测试文件合计 103 项）：一条指令一条记录（含关键词顺序）、多份地图条数相加、
关键词退化为写法、缺展示名、空白展示名、风险档收窄、无写法跳过、坏文件与旧版本跳过、
目录名解码失败只丢那一份、空目录返回空表。真数据冒烟：2 个插件 150 条。
