## 落地

新增 `apps/commandMap.js`：`syncCommandMaps()` 是唯一入口，启动、每日、票 06 的手动更新都调它。
启动同步挂在构造函数里，但**模块级开关保证全进程只排一次**——插件构造函数每条消息都会跑一遍；
延迟 10 秒等框架就绪，`unref()` 掉定时器。每日同步走框架的 `this.task`（`0 30 4 * * *`），
不自己 `setInterval`，否则热重载会叠出第二个定时器。

`syncMaps` 改成**不抛错**：索引拉不下来时记日志、累加失败计数、照常返回结果。失败计数与
`missing`（装在本机但地图仓没有的插件）、`revision`、`lastOkAt` 一起落到
`data/chatgpt/map-state.json`，写失败只记警告，不把一次成功的同步变成失败。

「这一轮算不算失败」的口径：有该下的却一份都没下成 → 失败；一份都没该下的、或下了哪怕一份 → 成功（计数归零）。
只认「一份都没成」，是因为地图之间互相独立，部分成功时用户看到的数据确实变新了。

**本机插件 = `plugins/` 下带 `package.json` 或 `index.js` 的目录名**，不是 package.json 里的 name：地图仓按仓库名发地图，
Yunzai 也按目录名认插件。只看 `package.json` 会漏掉没写这个文件的插件（线上「bujidao」就是这样整份地图没同步）。
排除 Yunzai 自带的 `adapter/example/other/system`——它们不是插件包，
留在清单里会让「缺失」永远有噪音。

`DEFAULT_INDEX_URL` 定义在地图核心并导出，`readIndex` 在配置为空时用它；测试断言这个真实值，
改错默认地址会直接红。`shouldNotifyFailures(n)` 是纯函数（`n > 0 && n % 3 === 0`），提醒文案带上最近一次错误。

真实数据验收（本地起静态服务喂 git blob 原文，即 GitHub 实际返回的字节）：
首轮 29 份待更新、26 份落地、3 份失败（失败源于地图仓数据问题，见下）、`ok=true`、`failures=0`；
第二轮只发一个索引请求、26 份判为已是最新。断网时连跑两轮：不抛错、`failures` 1→2、状态文件照常落盘。

### 验证时踩到的一个假警报

冒烟时先看到 `Atlas` / `miao-plugin` / `yenai-plugin` 三份「内容哈希不符」，差点当成地图仓的数据缺陷。
排查后确认是**本机地图仓克隆停在护栏 PR 之前**：那三份按 CRLF 检出，而索引是按 LF 算的哈希。
快进到最新 `main` 后按仓库 blob 校验 29/29 全部相符，发布链路没有问题。

留个教训：校验哈希要用**仓库里存的内容**（`git show HEAD:<path>`），别用工作区文件——
Windows 的 `core.autocrlf` 会让两者永久对不上，且本地看哪边都「自洽」。

测试 13 项（`test/commandMap.test.mjs` 的「同步状态」「本机插件」「开关判定」三块）：默认地址断言、不传地址用默认源、成功后状态落盘、
索引拉不下来不抛且计数累加、一份没下成算失败、部分成功算成功、状态文件损坏降级、
提醒阈值、插件目录扫描排除内置与隐藏、目录不存在返回空表。
